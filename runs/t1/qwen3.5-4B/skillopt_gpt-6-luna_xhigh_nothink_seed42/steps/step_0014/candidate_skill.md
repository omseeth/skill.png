# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check required inputs for each requested domain against the full conversation, compatible cached results, and the tool schema. Flight searches require a known route and departure date; hotel searches require a city, check-in date, and checkout date; restaurant searches require a city. Count a date only when its stated meaning matches the required field: an event date, such as a reunion or celebration, is not automatically a flight departure date or hotel check-in or checkout date. Never fill missing travel dates from examples, defaults, or assumptions. If required values are missing, make exactly one `seek_information(...)` call listing only all missing required values across the requested domains. Do not search or filter an incomplete domain, guess values, or ask for optional preferences as if they were required. Still perform every independent requested search or update whose own required inputs are complete in the same turn.
- Preserve user-provided dates, entity values, and casing. For a round trip, make two separate flight searches: one outbound and one with the route reversed for the return. Use each leg’s date as its `departure_date`; do not represent the return leg by setting `arrival_date` on the outbound search. Ask for an unknown endpoint rather than assuming a route. When a hotel stay is given as a check-in date plus an unambiguous duration in nights rather than a checkout date, call `adjust_date(date=<check-in date>, delta_days=<number of nights>)` and use its returned date as checkout; do not treat the duration as missing.
- Match arguments only to fields declared by the selected tool’s schema, with the expected type and cardinality. Never pass a preference as an unsupported extra argument or place it in an unrelated field. For range-shaped fields, encode an explicitly exact value as both endpoints (for example, `[n, n]`); encode a minimum rating or a request for at least or better as `[n, schema_max]`. Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`). For attraction searches, use each provided location field (`city` and/or `state`) in its matching schema field along with the requested category or name. Treat an unambiguous state name or standard two-letter U.S. postal abbreviation used as a location as a state value, not a city, and pass it unchanged in `state`. When the user names a specific attraction or landmark, pass its exact name in `attraction_name`; use `type` only for a requested category, not as a substitute inferred from the name. Pass neighborhood values in full as stated, including any city qualifier. A state alone is usable when the tool supports state-level search; do not ask for a city when it does.
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. If the user adds criteria, retrieve the closest compatible result, apply the matching filter, and save the updated result. Do not filter unrelated results; search for a requested entity or category that the cached results do not cover. Avoid retrieving unrelated results or repeating constraints in filters that were already applied in a search. Save each newly generated search or transformation result under a unique cache key. Use “No planning needed” only when cached results already satisfy every current request.
- Resolve each reply against the immediately preceding assistant question or proposal. Treat an answer that specifies or accepts a city, neighborhood, rating, amenity, or other filterable preference as a new active criterion, including brief affirmations accepting criteria proposed by the assistant. If a compatible cached result does not already satisfy that criterion, retrieve the closest compatible result, filter on only the newly added criteria, and save the update; do not use “No planning needed.” If the user names multiple locations to narrow a broad cached result, create a separate filter result for each location from that compatible result rather than starting a new search.
- Call `search_nearest` only when the user requests a proximity relationship between result types, such as asking for restaurants near attractions or attractions near a hotel. Merely requesting results from multiple domains for the same trip is not a proximity request. When proximity is requested, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
