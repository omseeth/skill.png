# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check mandatory inputs separately for each requested domain against the full conversation and relevant cached results. Flights require a departure date and a usable origin; hotels require a city plus check-in and checkout dates; restaurants require a city. Do not treat an event or occasion date as a flight departure date unless the user explicitly ties it to the flight. If lodging is requested for a trip with an explicit date interval, use the trip destination as the hotel city, the first date as check-in, and the later date as checkout unless the user provides different stay dates. Do not infer a checkout date or stay length from a single travel date. If any requested domain lacks required inputs, make exactly one `seek_information(...)` call listing only those missing values. Do not search or filter an incomplete domain, but do proceed in the same turn with independent requested domains whose required inputs are complete. Do not invent dates or room counts, or infer room count from guest count. Do not ask for optional preferences as if they were required.
- Preserve user-provided dates, entity values, and casing. For a round trip, search each leg separately, reverse the outbound route for the return, and use the return leg’s departure date. Ask for an unknown endpoint rather than assuming a route.
- Match arguments to the tool schema’s expected type, cardinality, and meaning. Map traveler count to `num_people` and room count to `num_rooms`; do not infer one from the other. Map locations to the field for their geographic level: for attraction searches, a supplied state or state abbreviation belongs in `state`, not `city`, and a city need not be supplied when the state is sufficient. Map amenities to the supported field that matches the user’s wording; do not add unrelated amenities or set multiple similar fields as a guess. In this interface, map “fitness center” to `has_fitness_class=True`. For a range-shaped field, encode one requested exact value as both endpoints (for example, `[n, n]` for one star rating); for a one-sided minimum or maximum, use the stated bound and the field’s supported endpoint for the unspecified side. Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`).
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. If the user adds criteria, retrieve the closest compatible result, apply the matching filter, and save the updated result. Do not filter unrelated results; search for a requested entity or category that the cached results do not cover. Avoid retrieving unrelated results or repeating constraints in filters that were already applied in a search. Save each newly generated search or transformation result under a unique cache key. Use “No planning needed” only when cached results already satisfy every current request.
- Resolve brief affirmations such as “yes” against the immediately preceding assistant question or proposal, and carry the accepted value into the relevant tool argument—not only named entities or categories, but also preferences and boolean amenities (for example, “yes” to breakfast means `breakfast_included=True`). Treat an accepted preference as a new actionable criterion: apply it to a compatible cached result with the matching filter and save the updated result; do not treat the affirmation as a no-op.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
