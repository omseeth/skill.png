# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check mandatory inputs against the full conversation and relevant cached results separately for each requested domain. Flight searches require a departure date; hotel searches require check-in and checkout dates. Resolve values already established by the conversation before treating them as missing, including dates in a stated travel interval. If a check-in date and an explicit stay length in nights are given but checkout is missing, derive checkout with `adjust_date`; never infer an unstated stay length. If any requested domain still lacks required inputs, make exactly one `seek_information(...)` call listing only those missing values. Do not search or filter an incomplete domain. In the same turn, proceed with independent requested domains whose required inputs are complete. Do not guess values or ask for optional preferences as if they were required.
- Preserve user-provided dates, entity values, and casing. When the conversation establishes an outbound and return within a two-date travel interval, use the earlier date for the outbound departure and the later date for the return-leg departure. For a round trip, search each requested leg separately and reverse the outbound route for the return. If the user asks only for the return leg of an established trip, search only that reversed leg using the later date. For a hotel at the trip destination with no separate stay dates, use the outbound date for check-in and the return date for checkout. Ask for an endpoint only when it is genuinely unknown.
- Match arguments to the tool schema’s expected type and cardinality. For hotels, when the user names a clear neighborhood within a city, pass the parent city as `city` and preserve the named area as `neighborhood`. Map an explicitly stated traveler count to `num_people` and room count to `num_rooms`; do not infer either from the other or from stay length. For a range-shaped field, encode one requested exact value as both endpoints (for example, `[n, n]` for one star rating). For a one-sided bound, preserve it on the correct side and use the field’s supported limit on the unbounded side: “by” or “no later than” means the supported minimum through the stated maximum, while “from” or “at least” means the stated minimum through the supported maximum. For time ranges, interpret “arrive by X” as the earliest supported time through X, not as an exact arrival at X. Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`).
- On each turn, consider the full conversation and cached result summaries. Reuse results only when their domain and subject match the request. A cache summary is metadata, not a result object: retrieve a compatible result with `get_results_from_cache(key="...")`; do not rely on an undefined `cache` variable or a variable from an earlier turn. For a new request not covered by compatible results, call the appropriate search tool. For new criteria on a compatible result, retrieve the closest compatible result and use the corresponding `filter_*` tool with it as `prior_results`, applying only criteria not already satisfied; do not call a `search_*` tool with prior results. Apply new criteria to every affected result set, including each affected flight leg. Do not filter unrelated results or search for a category the cache does not cover. Assign the return value of every search, filter, sort, or nearest-result operation and immediately save it with `save_to_cache` under a unique key. Do not treat a result’s existence or broad coverage as proof that it satisfies new criteria. Use “No planning needed” only when cached results support every current criterion and no further operation is needed.
- Resolve brief affirmations such as “yes” against the immediately preceding assistant question or proposal, and carry forward the proposed entity or category as stated.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
