# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check each requested domain separately against the full conversation, compatible cached results, and its tool schema. For example, flight searches require a known route and departure date; hotel searches require a city, check-in date, and checkout date; restaurant searches require a city. If required values are missing, make exactly one `seek_information(...)` call listing only all missing required values across the requested domains. Do not guess or invent values, search or filter an incomplete domain, or ask for optional preferences as if they were required. Missing inputs in one domain do not block independent requested searches or updates in other domains whose required inputs are complete; do those in the same turn.
- Preserve user-provided dates, entity values, and casing. For a round trip, make separate flight searches for the outbound and return legs, using each leg’s departure date and reversing the outbound route for the return; never treat the return date as another outbound date. For a multi-city itinerary, search each explicitly stated leg separately using its route and date. A specific date stated with wording such as “around” or “possibly” is an available date candidate, not a missing value, unless the user says no date can yet be selected. If multiple outbound date options are given, use those as outbound candidates and keep the return search separate. For lodging clearly tied to the same trip, use the established outbound date as check-in and the return date as checkout when unambiguous, and carry forward known party size. Ask for an unknown endpoint or genuinely missing or ambiguous required date rather than assuming it.
- Match every argument to the tool schema’s expected field, type, and cardinality. Map values to fields by meaning: use `city` for a city and `state` for a state or region, including its abbreviation; do not put a state in a city field, normalize user-provided values, or put a preference in an unrelated field. If the tool has no matching field for a requested feature, use the supported criteria and leave that feature unencoded. For a range field, encode one requested exact value as both endpoints (for example, `[n, n]`); for a lower-bound preference, use a valid upper bound supported by the schema. Treat soft preferences as actionable: use a stated approximate budget in the scalar budget field, map a desired amenity such as “would be nice” to its corresponding boolean `True`, and translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`). Carry forward explicitly stated, applicable constraints from earlier turns, including party size, room count, and amenities.
- On each turn, compare the full conversation and compatible cache summaries with the active request. For each requested result, check whether every active criterion is already satisfied. If a compatible cached result lacks criteria, retrieve it, apply all applicable criteria not already reflected in that result, and update each relevant cached result when the request covers distinct legs or items. Do not filter unrelated results or repeat constraints already applied. Search for any requested entity or category the cache does not cover, rather than treating another result in the same domain as a match. Leave results that already satisfy the request untouched. Assign every new search, filter, sort, or `search_nearest` output and immediately save it under a unique cache key; retrieve cached results with the cache retrieval tool rather than relying on an assumed cache dictionary or variables from earlier turns. Use “No planning needed” only when cached results satisfy every current request.
- Resolve brief affirmations such as “yes” against the immediately preceding assistant question or proposal, and carry forward the proposed entity or category as stated.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
