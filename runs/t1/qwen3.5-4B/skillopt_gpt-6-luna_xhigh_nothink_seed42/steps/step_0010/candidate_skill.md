# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check mandatory inputs against the full conversation and relevant cached results before planning calls. Flight searches require a departure date; hotel searches require check-in and checkout dates. If any requested domain lacks required inputs, make exactly one `seek_information(...)` call listing only the missing required values across the requested domains. Do not make partial searches or other planning calls until the user provides them. Do not guess or invent values, and do not ask for optional preferences as if they were required. Once required inputs are available, continue with independent searches whose inputs are available.
- Preserve user-provided dates, entity values, and casing. For a round trip, search each leg separately, reverse the outbound route for the return, and use the return leg’s departure date. Ask for an unknown endpoint rather than assuming a route.
- Match arguments to the tool schema’s supported parameters, meaning, expected type, and cardinality. Map each criterion only to a field that genuinely represents it; never invent an argument or repurpose an unrelated field merely because its type fits. If the tool has no matching parameter, omit that criterion rather than guessing (for example, atmosphere is not a neighborhood, and do not pass party size to a restaurant tool unless its schema supports party size). Treat an approximate single numeric budget (such as “around X” or “about X”) as amount X, mapping it to the schema-supported budget field; do not seek clarification unless the user gives an actual range or the tool requires information that is missing. Map a supplied state or state abbreviation for an attraction search to `state`, not `city`; a city need not be supplied when the state is sufficient. For a clearly named hotel or restaurant neighborhood or district, pass its parent city as `city` and preserve the named area in `neighborhood` (for example, `city="San Antonio"`, `neighborhood=["Downtown San Antonio"]`). For flight time ranges, use the accepted 12-hour `h:mm AM/PM` format, not `HH:MM:SS`. Interpret “by” or “no later than X” as the earliest supported time through X, and “from” or “at least X” as X through the latest supported time. For a range-shaped field, encode one requested exact value as both endpoints (for example, `[n, n]` for one star rating). Treat stated soft time-of-day preferences as actionable: translate them into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`).
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. If the user adds criteria, retrieve the closest compatible result, apply the matching filter, and save the updated result. Do not filter unrelated results; search for a requested entity or category that the cached results do not cover. Avoid retrieving unrelated results or repeating constraints in filters that were already applied in a search. Save each newly generated search or transformation result under a unique cache key. Use “No planning needed” only when cached results already satisfy every current request.
- Resolve brief affirmations such as “yes” against the immediately preceding assistant question or proposal. Carry the accepted service, subject, and criteria into the current request and perform any search or filter they require; an affirmation is not a no-op. Treat a later explicit correction or restriction (for example, “actually,” “instead,” or “only”) as superseding conflicting earlier preferences, and do not ask again for information the conversation already supplied. Resolve contextual follow-ups such as “what’s there?” or “tell me about that” against the immediately preceding proposal. When it names a place or category relevant to an existing result set, treat it as a new criterion: retrieve the compatible result, apply the matching filter using the proposed value, and save the updated result rather than treating the follow-up as a no-op. Resolve contextual location references such as “there,” “here,” and “nearby” against the most recent unambiguous destination or place in the full conversation. Use that known location for the new domain rather than treating the reference as missing or inventing a different place.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.

- Plan only travel services explicitly requested in the full conversation; a general trip, occasion, destination, or flight layover does not by itself request hotels, restaurants, or attractions. In addition to the date requirements above, flights need a usable origin and known route endpoints; hotels and restaurants need a city. Never pass `None` for a required field.
