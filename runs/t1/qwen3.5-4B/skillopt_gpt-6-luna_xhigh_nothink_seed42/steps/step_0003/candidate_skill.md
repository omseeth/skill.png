# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check mandatory inputs against the full conversation and relevant cache, and request dates only for domains the user actually requested. Flight searches require a departure date; hotel searches require check-in and checkout dates. Dates phrased approximately (for example, “around” a stated calendar date) still count as supplied; use the stated date without inventing alternatives. For a hotel at the destination of the same trip, if no separate stay dates are given, use the trip’s outbound date for check-in and return date for checkout. If checkout is missing but the user explicitly gave a stay length and check-in date, derive checkout with `adjust_date`; do not infer an unstated stay length. If any requested domain still lacks required inputs, make exactly one `seek_information(...)` call listing only those missing values. In the same turn, proceed with independent searches whose required inputs are complete; defer only incomplete domains and do not partially search them. Do not guess values or ask for optional preferences as if they were required.
- Preserve user-provided dates, named entities, and casing. For a round-trip flight search, make separate outbound and return searches: reverse the route for the return and pass each leg’s date as that search’s `departure_date`; do not represent the return only as the outbound search’s `arrival_date`. For a multi-city itinerary, read the stated route segments in order and map dates to their corresponding legs using the conversation’s chronology. Search every explicitly stated leg separately, in its given direction and using its provided departure date; do not force a multi-leg itinerary into a round trip or ask for dates or endpoints that are already clear. Ask only when a required leg endpoint or date is genuinely unknown.
- Match arguments to the tool schema’s expected type and cardinality, and map each preference only to a parameter with the same meaning. Map state names and abbreviations to `state`, not `city`; for attraction searches, a supplied state is sufficient when no city is given. Use the schema’s canonical spelling for categorical values (for example, `flight_class=["business"]`), while preserving user-provided dates and named entities exactly. For a range-shaped field, encode one requested exact value as both endpoints (for example, `[n, n]` for one star rating); for a one-sided bound, use the requested bound and the schema’s supported limit for the other endpoint (for example, a minimum rating of 3 on a 0–5 scale is `[3, 5]`). Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`). Do not approximate an unsupported or vague preference with an unrelated field (for example, do not interpret “kid-friendly” as pet-friendly); omit an unmatched optional parameter rather than inventing a value.
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. Before returning “No planning needed,” compare every current request and constraint with the cached results: a result’s existence, item count, or broad coverage does not establish that it satisfies a criterion unless the summary explicitly supports that criterion. If the user adds criteria, retrieve the closest compatible result and apply all newly stated criteria in the same compatible search or filter call, to every affected result set (including each affected flight leg). Reapply a criterion only when the compatible cached result does not already satisfy it. Do not filter unrelated results; search for an entity or category the cache does not cover. Avoid retrieving unrelated results or repeating constraints already applied in a search. Save each newly generated search or transformation result under a unique cache key.
- Resolve brief affirmations such as “yes” against the immediately preceding assistant question or proposal, and carry forward the proposed entity or category as stated.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
