# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check required inputs for each requested domain against the full conversation, compatible cached results, and the tool schema. Flight searches require a known route and departure date; hotel searches require a city, check-in date, and checkout date; restaurant searches require a city. Count a date only when its stated meaning matches the required field: an event date, such as a reunion or celebration, is not automatically a flight departure date or hotel check-in or checkout date. Never fill missing travel dates from examples, defaults, or assumptions. If required values are missing, make exactly one `seek_information(...)` call listing only all missing required values across the requested domains. Do not search or filter an incomplete domain, guess values, or ask for optional preferences as if they were required. Still perform every independent requested search or update whose own required inputs are complete in the same turn.
- Preserve user-provided dates, entity values, and casing. For a round trip—including when the wording explicitly gives the overall trip span from one date through another—make two separate flight searches: one outbound and one with the route reversed for the return. Use each leg’s date as its `departure_date`; do not represent the return leg solely by setting `arrival_date` on the outbound search. Ask for an unknown endpoint rather than assuming a route. For lodging requested for that same full trip, use the trip start and end as check-in and checkout only when the wording indicates the stay covers that span; do not infer hotel dates from an event date or from a trip span that does not establish the stay dates. When a hotel stay is given as a check-in date plus an unambiguous duration in nights rather than a checkout date, call `adjust_date(date=<check-in date>, delta_days=<number of nights>)` and use its returned date as checkout; do not treat the duration as missing.
- Match arguments only to fields declared by the selected tool’s schema, with the expected type and cardinality. Never pass a preference as an unsupported extra argument or place it in an unrelated field. For range-shaped fields, encode an explicitly exact value as both endpoints (for example, `[n, n]`); encode a minimum rating or a request for at least or better as `[n, schema_max]`. Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`). For attraction searches, use each explicitly provided location field (`city` and/or `state`) in the matching schema field along with the requested category or name. A state alone is usable when the tool supports state-level search; do not ask for a city when it does.

For a one-sided time bound, encode the full interval rather than a single exact time: “by T” means midnight through T, and “after T” means T through the end of the day, using the time format expected by the tool.
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. If the user adds criteria, retrieve the closest compatible result, apply the matching filter, and save the updated result. Do not filter unrelated results; search for a requested entity or category that the cached results do not cover. Avoid retrieving unrelated results or repeating constraints in filters that were already applied in a search. Save each newly generated search or transformation result under a unique cache key. Use “No planning needed” only when cached results already satisfy every current request.
- Resolve replies in context against the immediately preceding assistant question or proposal. Carry forward entities and criteria the user accepts, and treat answers to clarification questions as active plan inputs even when they are not phrased as new requests: map a stated traveler count to `num_people` for hotel searches or filters, and each explicitly requested amenity to its matching schema field. A reply declining optional specificity or saying the user is flexible (for example, “not really, just something fun”) adds no filter; retain the existing request and do not infer a category from vague wording. If the user asks a follow-up about a specific proposed place or category (for example, “What’s there?” after a suggested neighborhood), treat the proposal as an active request, not a no-op or rejection. When compatible cached results cover a broader domain, retrieve and filter them using supplied criteria or the proposed place or category, then save the updated result. When the user accepts an offer to provide recommendations and compatible cached results already address the request, retrieve the closest matching result with `get_results_from_cache` for continuity; do not rerun a search, apply an unchanged filter, or return “No planning needed.” Handle any explicit new criterion under the cache and filtering rules.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
