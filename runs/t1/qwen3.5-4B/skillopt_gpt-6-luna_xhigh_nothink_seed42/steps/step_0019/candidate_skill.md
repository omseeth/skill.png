# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check required inputs for each requested domain against the full conversation, compatible cached results, and the tool schema. Flight searches require a known route and departure date; hotel searches require a city, check-in date, and checkout date; restaurant searches require a city. Count a date only when its stated meaning matches the required field: an event date, such as a reunion or celebration, is not automatically a flight departure date or hotel check-in or checkout date. Never fill missing travel dates from examples, defaults, or assumptions. If required values are missing, make exactly one `seek_information(...)` call listing only all missing required values across the requested domains. Do not search or filter an incomplete domain, guess values, or ask for optional preferences as if they were required. Still perform every independent requested search or update whose own required inputs are complete in the same turn.
- Preserve user-provided dates, entity values, and casing. For a round trip, make two separate flight searches: one outbound and one with the route reversed for the return. Use each leg’s date as its `departure_date`; do not represent the return leg by setting `arrival_date` on the outbound search. Ask for an unknown endpoint rather than assuming a route. When a hotel stay is given as a check-in date plus an unambiguous duration in nights rather than a checkout date, call `adjust_date(date=<check-in date>, delta_days=<number of nights>)` and use its returned date as checkout; do not treat the duration as missing.
- Match arguments only to fields declared by the selected tool’s schema, with the expected type and cardinality. Carry explicitly stated or unambiguous values into matching supported optional fields, but do not ask for optional values that are absent. Translate common explicit shorthand into supported schema values: “non-stop” or “no layovers” means `num_layovers=[0]`; “solo” or “one traveler” means hotel `num_people=1`. Pass stated party and room counts to their matching fields, but do not infer either when unstated or assume `num_rooms=1` from a solo traveler. Never pass a preference as an unsupported extra argument or place it in an unrelated field. For range-shaped fields, encode an explicitly exact value as both endpoints (for example, `[n, n]`); encode a minimum rating or a request for at least or better as `[n, schema_max]`. Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`). For attraction searches, use each explicitly provided location field (`city` and/or `state`) in the matching schema field along with the requested category or name. When wording unambiguously identifies a state—for example, “in CO” or “in Colorado”—pass it as `state`, not `city`, preserving the user’s exact text. A state alone is usable when the tool supports state-level search; do not ask for a city when it does.
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. If the user adds criteria, retrieve the closest compatible result, apply the matching filter, and save the updated result. Do not filter unrelated results; search for a requested entity or category that the cached results do not cover. Avoid retrieving unrelated results or repeating constraints in filters that were already applied in a search. Save each newly generated search or transformation result under a unique cache key. Use “No planning needed” only when cached results already satisfy every current request.
- Resolve brief affirmations and other replies against the immediately preceding assistant question, proposal, or clarification. Carry forward the accepted proposal and the rest of the request, and treat explicit answers—such as a date, class, rating, amenity, allergy, cuisine, neighborhood, or party size—as active information. Apply each criterion to every relevant requested result or itinerary stop. If compatible cached results do not already satisfy a new criterion, retrieve the closest compatible result, filter it using that criterion, and save the update; an unfiltered cached result does not satisfy it. Do not use “No planning needed” while any requested criterion or proximity relationship remains unmet.

Treat acceptance of an offer to provide recommendations or perform an action as an active request: fulfill the proposal, retrieving the closest compatible cached result when available or performing the proposed search or transformation otherwise. Do not treat acceptance as a no-op merely because it adds no new filter.
- For recommendations near another result type, ensure compatible results for both types are available, then call `search_nearest` and save its result. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
