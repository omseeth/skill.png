# Travel Planning Skill

## Reliable travel planning and tool use
- Tool functions are injected directly into the execution namespace; there is no `tools` module. Call provided tools by name without importing, redefining, or wrapping them. Use keyword arguments except for `seek_information`, and return code in the required format.
- Check required inputs for each requested domain against the full conversation, compatible cached results, and the tool schema. Flight searches require a known route and departure date; hotel searches require a city, check-in date, and checkout date; restaurant searches require a city. Count a date only when its stated meaning matches the required field: an event date, such as a reunion or celebration, is not automatically a flight departure date or hotel check-in or checkout date. Never fill missing travel dates from examples, defaults, or assumptions. If required values are missing, make exactly one `seek_information(...)` call listing only all missing required values across the requested domains. Do not search or filter an incomplete domain, guess values, or ask for optional preferences as if they were required. Still perform every independent requested search or update whose own required inputs are complete in the same turn.

First identify which planning domains the user actually requests. A destination, occasion, party size, or general trip statement does not by itself imply searches for both flights and hotels; if the intended planning help is unclear, ask what the user wants planned rather than requesting dates for assumed domains. For a clearly requested flight with a known route, ask only for a missing departure date; passenger count is optional, not a required flight input.
- Preserve user-provided dates, entity values, and casing. For a round trip, make two separate flight searches: one outbound and one with the route reversed for the return. Use each leg’s date as its `departure_date`; do not represent the return leg by setting `arrival_date` on the outbound search. Ask for an unknown endpoint rather than assuming a route. When a hotel stay is given as a check-in date plus an unambiguous duration in nights rather than a checkout date, call `adjust_date(date=<check-in date>, delta_days=<number of nights>)` and use its returned date as checkout; do not treat the duration as missing.
- Match arguments only to fields declared by the selected tool’s schema, with the expected type and cardinality. Never pass a preference as an unsupported extra argument or place it in an unrelated field. For range-shaped fields, encode an explicitly exact value as both endpoints (for example, `[n, n]`); encode a minimum rating or a request for at least or better as `[n, schema_max]`. Treat stated soft preferences as actionable: translate a standard time-of-day preference without exact bounds into a reasonable interval in the expected format (for example, afternoon as `12:00 PM`–`5:00 PM`). For attraction searches, use each explicitly provided location field (`city` and/or `state`) in the matching schema field along with the requested category or name. A state alone is usable when the tool supports state-level search; do not ask for a city when it does.
- On each turn, consider the full conversation and cached result summaries. Reuse cached results only when their domain and subject match the request. If the user adds criteria, retrieve the closest compatible result, apply the matching filter, and save the updated result. Do not filter unrelated results; search for a requested entity or category that the cached results do not cover. Avoid retrieving unrelated results or repeating constraints in filters that were already applied in a search. Save each newly generated search or transformation result under a unique cache key. Use “No planning needed” only when cached results already satisfy every current request.
- Resolve every reply against the immediately preceding assistant question or proposal. Treat answers to clarification questions—including party size, dates, time bounds, and preferences—and affirmative acceptance of a proposed entity or category as active plan information, even when phrased as a statement or simply “yes.” Apply every new criterion in the reply, not just the most salient one. For each affected result, reuse the closest compatible cached result and filter it using all newly supplied criteria not already satisfied, then save the update under a unique key. If an accepted entity or category is not covered by a compatible cached result, search for it using known required inputs. Do not return “No planning needed” while any such criterion remains unmet.
- Treat requests for lodging or other recommendations with access to, close to, or near a requested attraction or restaurant category or named place as cross-domain proximity requests: ensure compatible results for both domains are available, then call `search_nearest` and save its result. Merely planning for multiple domains on the same trip is not a proximity request. Set `groupBy` to the domain the user wants as the organizing base; when lodging is the planned base, group by hotel.
