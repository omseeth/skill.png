# Travel Planning Skill

## Incremental planning and cache use

- When a reply only declines optional specificity (such as “not really” or “I’m flexible”) or accepts an offer to show recommendations, keep the original requested scope active and do not infer a filter from an assistant’s suggestion. If a listed, compatible result already covers that scope, retrieve it into a local variable for the continued response; do not search or filter again, print `No planning needed`, or retrieve unrelated, unchanged domains.

- Before emitting code, audit the planned calls against the latest turn and full conversation: for each new request or accepted preference, identify its intended item, domain, relation, and schema-supported argument, then verify that a planned call includes it. Do not reprocess unchanged domains. Use only a listed, compatible cache result for refinement; if none exists and mandatory inputs are available, search instead of filtering. After the audit, use `print("No planning needed")` only if no requested action or constraint remains unsatisfied by valid cached results.
- Treat the latest user turn as an update to the trip plan. Check cache coverage separately for each requested domain and constraint, using relevant conversation context. For an affected domain, retrieve the latest relevant valid result with `get_results_from_cache(key="...")` into a local variable and pass it as `prior_results` when required. Apply only the newly introduced constraint to results that already represent earlier criteria; search when a needed result is unavailable. Do not redo unaffected domains or rely on variables from earlier executions.
- A cached base result does not satisfy a newly requested constraint, and a result for one domain does not satisfy a request for another. Use `print("No planning needed")` only when relevant, valid cached results already satisfy every requested action and constraint.
- Bind the exact return value of every search, filter, sort, and nearest-results call to a variable, then save it with `save_to_cache` under a unique, descriptive key. Save refined results under a new key. Do not substitute hand-built dictionaries or redefined models for tool result objects.

## Represent flight legs separately
- Treat each explicitly described flight leg as its own search, using that leg’s origin, destination, and departure date. When a trip between two cities is given as a start-to-end date span, treat the first date as outbound and the second as return unless the user explicitly describes a one-way or multi-city trip. Search the return separately with the route reversed; do not combine the dates into one outbound search or use an unsupported `return_date` argument. If the user requests only the return leg and the outbound route is known, reverse that route and use the return date as the return leg’s `departure_date`; do not search the outbound leg. Apply an explicitly requested flight class and other non-direction-specific preferences to every applicable leg; if directional results are cached, retrieve and refine each leg independently.
- At follow-up, treat each flight leg as a separate cache-coverage unit. Leave a valid, unchanged leg untouched; search or filter only legs that are missing or affected by a new constraint, and save each resulting leg separately.
- For multi-city trips, preserve the stated destination sequence and match each date to its corresponding leg. Do not combine dates or invent arrival dates. Pass values to `airline` only when they identify a specific airline; do not treat qualitative descriptions such as “kid-friendly” as airline names or invent a matching airline.

## Validate tool arguments and preserve user intent
- Check each tool’s schema for supported argument names and required fields. Use the exact field that matches the user’s meaning; do not invent aliases. For example, hotel star requirements use `stars`, a region belongs in `state`, a city in `city`, and a named attraction in `attraction_name`. Use the schema’s exact amenity field (such as `has_laundry_service`) when that preference is stated. Hotel searches require check-in and check-out dates, and hotel filters require `prior_results`.
- Carry forward relevant details from the conversation and include explicitly supplied criteria in the appropriate call. Send only schema-supported parameters; do not infer amenities, ratings, or other preferences. Do not infer exact party or room counts from broad descriptions such as “family.” Treat “solo” as one traveler only when a supported traveler-count field is available; do not infer a room count from it. A traveler count is not a flight-search parameter unless the schema provides one.
- For a cache refinement, use the most refined compatible result under a key actually listed in the cache summary: retrieve it into a local variable and pass that exact result as `prior_results` to the matching filter with only the newly introduced criteria. Do not rely on variables from earlier executions or resend criteria already represented in the result. Save the refinement under a new key. If no compatible base is listed and mandatory inputs are available, make one search with all currently active, explicit, schema-supported criteria for that item rather than a broad search followed by redundant filters.
- For fields whose schema represents a minimum/maximum range, supply both bounds. An exact N-star hotel request uses `stars=[N, N]`, not a single-value list.
- Map an explicitly stated numeric party or guest count to `num_people` when the hotel schema supports it; map an explicitly stated room count to `num_rooms`. Do not infer one count from the other or infer a room count from a broad description such as “family.” Treat a state or province abbreviation as a region and use `state`, not `city`, while preserving the supplied abbreviation.
- Call the provided tool functions directly. Do not import tool modules or define or redefine tool functions or input models.

## Proximity between travel domains
- Call `search_nearest` only when the user explicitly requests proximity between supported domains. Before calling it, verify that each cached result covers the specific requested target, not merely the same domain or city. For example, a generic city attraction search does not cover a separately named attraction; search for the named attraction using `attraction_name` unless the cache summary shows that exact target is already covered.
- Pass the relevant result objects for the two domains being compared. Set `groupBy` to the domain whose candidates the user wants ranked or recommended (the focal domain), not the reference domain: hotels near an attraction use `groupBy="hotel"`, while restaurants near a hotel use `groupBy="restaurant"`.
- Interest in visiting or dining at a place alone does not imply a proximity request or require a nearest-results call.

## Missing mandatory information
Check mandatory inputs separately for every active requested action and domain against explicit values in the full conversation; related context does not automatically satisfy a required field. Do not invent missing values or use defaults. If any action lacks mandatory information, make one `seek_information` call asking only for those missing inputs. Do not search that incomplete action, but still execute and save other independently requested actions whose own mandatory inputs are complete. For a hotel stay at an unambiguous single trip destination, use explicitly supplied trip start and end dates as check-in and check-out when no separate hotel dates were given. If the destination or date relationship is ambiguous, ask instead. Optional preferences are not mandatory inputs.
