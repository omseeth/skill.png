# Travel Planning Skill

## Incremental planning and cache use
- Treat the latest user turn as an update to the full trip plan. Before planning, inventory every requested action and item from the full conversation, including replies to assistant questions, distinct flight legs, and explicitly requested lodging destinations or stays. Check cache coverage separately for each item and constraint. For an affected item, retrieve the latest relevant valid result with `get_results_from_cache(key="...")` into a local variable and pass it as `prior_results` when required. When a cached result already represents earlier criteria, apply each newly introduced constraint using the appropriate supported filter argument and ensure the call actually includes it; search when a needed result is unavailable. Do not skip uncovered requested items, redo unaffected domains, or rely on variables from earlier executions.
- A cached base result does not satisfy a newly requested constraint, and a result for one domain does not satisfy a request for another. Use `print("No planning needed")` only when relevant, valid cached results already satisfy every requested action and constraint.
- Bind the exact return value of every search, filter, sort, and nearest-results call to a variable, then save it with `save_to_cache` under a unique, descriptive key. Save refined results under a new key. Do not substitute hand-built dictionaries or redefined models for tool result objects.

## Represent flight legs separately
- Treat each explicitly described flight segment as its own search, using that leg’s origin, destination, and departure date. For a round trip, search outbound and return separately, reversing the route for the return; do not use an unsupported `return_date` argument or treat the return date as another outbound date. Apply an explicitly requested flight class to both directions; if directional results are already cached, retrieve and filter each direction.
- For multi-city trips, preserve the stated destination sequence and match each date to its corresponding leg. Do not combine dates or invent arrival dates.

## Validate tool arguments and preserve user intent

- Match location granularity to the schema: use `state` when the user gives a state or region rather than a city. For a named neighborhood within a city, use the containing city in `city` and the named area in `neighborhood`; preserve the user’s supplied entity text, including city qualifiers in compound neighborhood labels. For attraction searches, a state name or abbreviation supplied without a city belongs in `state`, not `city`.
- When the schema represents a minimum-only rating preference as a range, use that minimum and the scale’s upper bound (for example, on a 1–5 scale, “at least 3” becomes `[3, 5]`). When `stars` is a minimum/maximum pair, encode an exact N-star request as `[N, N]`.
- Check each tool’s schema for supported argument names and required fields. Use the exact field that matches the user’s meaning; do not invent aliases. For example, hotel star requirements use `stars`, a region belongs in `state`, a city in `city`, and a named attraction in `attraction_name`. Use the schema’s exact amenity field (such as `has_laundry_service`) when that preference is stated. Hotel searches require check-in and check-out dates, and hotel filters require `prior_results`.
- Carry forward relevant details from the conversation and include explicitly supplied criteria in the appropriate call. Send only schema-supported parameters; do not infer amenities, ratings, or other preferences. Do not infer exact party or room counts from broad descriptions such as “family.” Treat “solo” as one traveler only when a supported traveler-count field is available; do not infer a room count from it. A traveler count is not a flight-search parameter unless the schema provides one.
- When refining a cached result, do not resend criteria already represented in that result; apply the newly introduced preference with the appropriate filter.

## Hotel proximity to attractions
- If the user explicitly requests hotel access or proximity to an attraction, check whether relevant attraction results are available; search for any missing results, then call `search_nearest` with both the hotel and attraction result objects, grouped by the requested primary domain. Interest in visiting an attraction alone does not imply a request for proximity or require a nearest-results call.

## Missing mandatory information
Build the requested actions from the full conversation, then check mandatory inputs separately for each requested domain. If information is missing for one or more domains, make one `seek_information` call asking only for those missing mandatory inputs; do not search a domain whose own mandatory inputs are incomplete. Still perform and cache searches for other requested domains whose mandatory inputs are complete. If the user gives an exact hotel check-in date and an explicit stay length in nights, use `adjust_date` to derive check-out; do not ask for a date that can be derived this way. Vague timing such as “a weekend” does not supply exact dates or a stay length. Do not invent values or use defaults; optional preferences are not mandatory inputs.

## Execute tools directly
- Call the provided tool functions directly; do not import tools, alter module paths, or define or redefine tool functions or their models. Use `print("No planning needed")` only when valid cached results already satisfy the entire request, and never append it after performing searches, filters, sorts, or nearest-results calls.
