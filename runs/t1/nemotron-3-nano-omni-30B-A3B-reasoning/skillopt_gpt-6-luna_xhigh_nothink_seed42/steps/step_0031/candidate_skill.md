# Travel Planning Skill

## Incremental planning and cache use

- Resolve the latest user turn against the immediately preceding assistant question or suggestion and all still-pending requests. Interpret replies in context: a direct answer can supply the asked-for criterion or introduce a new target or criterion; an affirmative answer to a concrete yes/no question proposing an action in a supported travel domain makes that action pending even if the domain was not previously active. Carry forward the named target or type and relevant location; search if mandatory inputs are available, otherwise seek the missing information. Asking what is available about a suggested area likewise makes that area an actionable target. Apply “both” to every still-pending referenced domain, and apply other still-valid criteria independently to every named location, creating a distinct result for each. When the user accepts an offer, perform the offered action; an accepted proximity recommendation requires `search_nearest` with the relevant domain results, while mere interest in a place alone does not request proximity.
- Build a complete checklist of every new and still-pending action by domain, target, location, relation, schema-supported argument, and—where applicable—flight leg. Apply every new constraint. Assess each domain, location, and leg independently; leave unchanged domains alone, recheck previously blocked items when a reply supplies missing information, and do not rely on variables from earlier executions.
- For each checklist item, use only an exact listed compatible cache result. If it already covers the requested action and every constraint—including when the latest turn adds no criterion and recommendations are expected—retrieve it by its exact listed key into a local variable and use it directly; do not search or filter again. If the request adds a constraint to an existing target, retrieve the latest listed compatible result that covers the prior criteria and apply only the new constraint with the appropriate filter, passing it as `prior_results` when required. A base result that lacks the new constraint, or a result for a different target or domain, is not coverage. If no compatible result exists, search with all applicable stated criteria only when mandatory inputs are explicit. Do not infer missing mandatory inputs or use defaults: make one `seek_information` call for missing mandatory inputs across blocked items while proceeding with other ready items. Mark an item complete only when its constraints are covered by a valid compatible cached result or have been applied by the required tool call. Use `print("No planning needed")` only when no requested action remains pending and valid cached results cover every requested constraint.

- Resolve elliptical latest turns against the immediately preceding assistant question and all still-pending user requests before deciding what action is needed. Interpret replies in the context of the assistant's concrete question or suggestion, not only their literal wording: a direct answer can supply the asked-for amenity or preference, and asking what is available after an area is suggested makes that area an actionable search target. A direct answer can also introduce a new destination, neighborhood, cuisine, amenity, or other criterion; it is not merely confirmation that an existing base result is adequate. If the reply says a criterion applies to “both,” apply it independently to every still-pending domain referenced in context (for example, hotels and restaurants), using each domain’s appropriate filter and latest compatible cached result; do not apply it only to the last-mentioned domain. If the answer names multiple locations, apply the other still-valid criteria independently to each location and create a distinct result for each.
- Treat the latest user turn as an update to the trip plan. Check cache coverage separately for each requested domain and constraint, using relevant conversation context. For an affected domain, retrieve the latest relevant valid result with `get_results_from_cache(key="...")` into a local variable and pass it as `prior_results` when required. Apply only the newly introduced constraint to results that already represent earlier criteria; search when a needed result is unavailable. Do not redo unaffected domains or rely on variables from earlier executions.
- A cached base result does not satisfy a newly requested constraint, and a result for one domain does not satisfy a request for another. Use `print("No planning needed")` only when relevant, valid cached results already satisfy every requested action and constraint.

- If the latest turn adds no criterion and a compatible listed cache result already covers the outstanding request—including when the user says they are flexible or accepts an offer to provide recommendations—retrieve that result with its exact listed key into a local variable and use it directly. Do not search or filter again, and do not use `print("No planning needed")` in place of retrieving a result the user is expecting.
- Bind the exact return value of every search, filter, sort, and nearest-results call to a variable, then save it with `save_to_cache` under a unique, descriptive key. Save refined results under a new key. Do not substitute hand-built dictionaries or redefined models for tool result objects.

## Represent flight legs separately
- Treat each explicitly described flight segment as its own search, using that leg’s origin, destination, and departure date. For a round trip with outbound date D1 and return date D2, search origin-to-destination with `departure_date=[D1]`, then destination-to-origin with `departure_date=[D2]`. D2 is the return leg’s departure date: do not send it as `arrival_date` or `return_date`, or add it to the outbound date list. Do not infer `flight_class` from trip purpose (for example, a business trip); apply a class to both legs only when the user explicitly requests it. Reuse a cached directional result only if it covers that leg and its criteria.
- For multi-city trips, preserve the stated destination sequence and match each date to its corresponding leg. Do not combine dates or invent arrival dates.

## Validate tool arguments and preserve user intent
- Check each tool’s schema for supported argument names and required fields. Use the exact field that matches the user’s meaning; do not invent aliases. For example, hotel star requirements use `stars`, a region belongs in `state`, a city in `city`, and a named attraction in `attraction_name`. Use the schema’s exact amenity field (such as `has_laundry_service`) when that preference is stated. Hotel searches require check-in and check-out dates, and hotel filters require `prior_results`.

- Validate value encoding as well as argument names. For fields documented as lower/upper endpoint lists, represent an exact requested value x as `[x, x]`; do not pass a scalar or singleton list, widen the value, or treat it as a minimum. Follow the schema for non-exact bounds and do not invent endpoints.
- Parse locations hierarchically when the user gives both a city and an area within it: use the parent city in `city` and pass the named district or area verbatim in `neighborhood` when supported. Preserve the complete location label rather than shortening it or passing the combined city-and-area phrase as the city; for example, a request for Downtown Tucson uses `city="Tucson"` and `neighborhood=["Downtown Tucson"]`.
- Disambiguate closely related amenity fields using the tool’s phrase-to-field semantics rather than casual synonym matching. When a hotel schema exposes both fields, map “fitness center” to `has_fitness_class` and a literal request for a “gym” to `gym_present`.
- Carry forward relevant details from the conversation and include explicitly supplied criteria in the appropriate call. Send only schema-supported parameters; do not infer amenities, ratings, or other preferences. Do not infer exact party or room counts from broad descriptions such as “family.” Treat “solo” as one traveler only when a supported traveler-count field is available; do not infer a room count from it. A traveler count is not a flight-search parameter unless the schema provides one.
- When refining a cached result, do not resend criteria already represented in that result; apply the newly introduced preference with the appropriate filter.

## Proximity between travel domains
- Call `search_nearest` only when the user explicitly requests proximity between supported domains. Before calling it, verify that each cached result covers the specific requested target, not merely the same domain or city. For example, a generic city attraction search does not cover a separately named attraction; search for the named attraction using `attraction_name` unless the cache summary shows that exact target is already covered.
- Pass the relevant result objects for the two domains being compared. Set `groupBy` to the domain whose candidates the user wants ranked or recommended (the focal domain), not the reference domain: hotels near an attraction use `groupBy="hotel"`, while restaurants near a hotel use `groupBy="restaurant"`.
- Interest in visiting or dining at a place alone does not imply a proximity request or require a nearest-results call.

## Missing mandatory information
For each planned tool action, first identify its non-optional schema fields and verify that each has an explicit value in the conversation. If any required value is missing, do not make that search or refinement call. Do not invent dates from the current date, trip purpose, birthday, wedding, or event context; an event date is not a flight departure date unless the user explicitly says so. Hotel check-in and check-out dates must both be explicit. Ask for missing mandatory values in one `seek_information` call across blocked domains, and do not ask for unspecified optional filters (such as an arrival-time range). Assess readiness independently for each requested domain, city, or flight leg, and proceed with ready actions even if another is blocked. Related context does not automatically satisfy a required field: for example, cuisine or budget does not supply a restaurant city.

Treat cache coverage as evidence, not an assumption: a cache key, code comment, or prior search does not prove that a newly stated value is covered. Keep each new constraint pending until its exact target and value appear in a compatible result or in a tool call that applies it. For a changed preference, retrieve the latest listed compatible result, apply the delta to that result, and save the refinement; do not skip the action or substitute a new search when the request is only a refinement.

When the user accepts an assistant offer, resolve the offer from the conversation and perform that specific action. In particular, an accepted proximity recommendation requires `search_nearest` with the relevant cached domain results; it is not complete merely because those results exist. Match each update to its target result: a party-size update after a nearest-hotel result belongs on that result with the supported party-count filter, not on an unrelated base hotel search.

Keep work scoped to changed and still-pending domains. Do not search or filter flight legs during a hotel- or attraction-only update. When a new airline or cabin preference applies to already searched legs, refine the compatible cached leg results rather than rebuilding the searches, and preserve the user’s literal airline code. Treat state abbreviations as states, not cities.

Use the runtime-provided tool functions directly; do not import modules to access tools or cache helpers. Do not guess result fields, inspect or print model contents, or add presentation code that can fail after the required tool calls. Bind and save the exact tool results, and do not declare the plan complete until every ready pending action has actually been handled.
