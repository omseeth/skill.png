# Travel Planning Skill

## Incremental planning and cache use
- Treat the latest user turn as a delta to the full conversation. Resolve short affirmative replies (such as “yes” or “that sounds great”) against the immediately preceding assistant question or offer before identifying requested actions and checking cache coverage; treat the reply as accepting that scope. For each requested action, domain, and constraint, use the supplied cache summary as evidence and count a criterion as covered only when it is explicitly shown. Choose a cache key that actually appears in the summary; when several valid results exist, use the most refined relevant result that covers the earlier criteria. If an action or new constraint is not covered, retrieve the relevant result with `get_results_from_cache(key="...")` into a local variable and apply only the new constraint with the appropriate filter, passing it as `prior_results` when required. Save refinements under a new key. Search when a suitable base result is unavailable. Do not guess keys, pass missing or `None` results to filters, assume a result for one request covers a different request, or redo unaffected domains; retrieval alone does not complete an update.
- A cached base result does not satisfy a newly requested constraint, and a result for one domain does not satisfy a request for another. Use `print("No planning needed")` only when relevant, valid cached results already satisfy every requested action and constraint.
- Bind the exact return value of every search, filter, sort, and nearest-results call to a variable, then save it with `save_to_cache` under a unique, descriptive key. Save refined results under a new key. Do not substitute hand-built dictionaries or redefined models for tool result objects.

## Represent flight legs separately
- Make a separate search for each distinct one-way flight segment, using that leg’s origin, destination, and departure date. For a round trip, search outbound and return separately, reversing the route for the return, and put each leg’s date in its `departure_date`; do not use `return_date`, put the return date in `arrival_date`, or combine outbound and return dates in one call. If dates are alternatives for the same leg, include all alternatives in that leg’s `departure_date` list in one call. Apply every flight preference stated without a directional limitation (such as class, departure-time window, airline, budget, or layover preference) to every applicable leg. If leg results are cached, retrieve and filter each leg independently for the new preference, then save each refinement separately. Apply a direction-specific preference only to the leg it names.
- For multi-city trips, preserve the stated destination sequence and match each date to its corresponding leg. Do not combine dates or invent arrival dates.

## Validate tool arguments and preserve user intent

- Send an optional parameter only when the user explicitly supplied that preference; do not treat a tool’s default as a user request. If a qualitative preference has no supported matching field, do not approximate it with an unrelated field or value; use only criteria the schema supports. For range-valued fields, provide both bounds: “at least” or “minimum X” means `[X, scale maximum]`, while an exact rating of X means `[X, X]` (for example, on a 1–5 scale, a minimum of 4.5 is `[4.5, 5]`).
- Check each tool’s schema for supported argument names and required fields. Use the exact field that matches the user’s meaning; do not invent aliases. For example, hotel star requirements use `stars`, a region belongs in `state`, a city in `city`, and a named attraction in `attraction_name`. Use the schema’s exact amenity field (such as `has_laundry_service`) when that preference is stated. Hotel searches require check-in and check-out dates, and hotel filters require `prior_results`.
- Carry forward relevant details from the conversation and include explicitly supplied criteria in the appropriate call. Send only schema-supported parameters; do not infer amenities, ratings, or other preferences. Do not infer exact party or room counts from broad descriptions such as “family.” Treat “solo” as one traveler only when a supported traveler-count field is available; do not infer a room count from it. A traveler count is not a flight-search parameter unless the schema provides one.
- When refining a cached result, do not resend criteria already represented in that result; apply the newly introduced preference with the appropriate filter.

## Hotel proximity to attractions
- If the user explicitly requests hotel access or proximity to an attraction, check whether relevant attraction results are available; search for any missing results, then call `search_nearest` with both the hotel and attraction result objects, grouped by the requested primary domain. Interest in visiting an attraction alone does not imply a request for proximity or require a nearest-results call.

## Missing mandatory information

A flight search requires a departure date for each requested leg; a hotel search requires both check-in and check-out dates. Vague timing such as “last-minute” does not supply a date, and examples or assumed current dates are not valid substitutes.
Before searching, check the full conversation for all mandatory inputs required by each requested tool. If any are missing, do not invent values, use defaults, or run a partial search. Make one `seek_information` call asking only for the missing mandatory information across the requested domains; optional preferences are not mandatory inputs.
