# Travel Planning Skill

## Incremental planning and cache use

- Before emitting code, make a coverage checklist from the full conversation, treating the latest user turn as an update rather than a standalone request. Include every still-pending requested item and domain, each explicitly described flight leg, and each new or accepted constraint or cross-domain relation. Resolve short replies against the immediately preceding assistant question or proposal: an answer such as “yes,” “that sounds great,” or a cuisine preference can accept or specify a concrete item, criterion, or relation. For each checklist item, identify its intended target, domain, relation, and schema-supported argument, then verify the plan includes the appropriate call. Treat a request as outstanding unless a valid cached result covers that exact criterion. Do not reprocess unchanged or unrelated domains. Use only a listed, compatible cache result for refinement; if none exists and mandatory inputs are available, search instead of filtering. After the audit, use `print("No planning needed")` only if no requested action or constraint remains unsatisfied by valid cached results.
- Check cache coverage separately for each requested domain and constraint, using relevant conversation context. Copy cache keys exactly from the supplied cache listing; never guess a conventional key. Confirm the listed result is valid and its summary covers the requested domain and criteria—an unlisted new constraint is not satisfied. For an affected domain, retrieve the latest relevant compatible result with `get_results_from_cache(key="...")` into a local variable and pass it as `prior_results` when required. Apply only the newly introduced constraint to results that already represent earlier criteria. If no compatible listed result exists and mandatory inputs are available, search instead of filtering; never filter a missing or `None` result. Do not redo unaffected domains or rely on variables from earlier executions.
- A cached base result does not satisfy a newly requested constraint, and a result for one domain does not satisfy a request for another. Use `print("No planning needed")` only when relevant, valid cached results already satisfy every requested action and constraint.
- For every search, filter, sort, and nearest-results call, bind the exact returned object to a local variable and immediately save that same object with `save_to_cache` under a unique, descriptive key before using it downstream or finishing the plan. Save each refinement under a new key. For refinements, retrieve the cached result separately into a local variable and pass it as `prior_results`; do not nest cache retrievals inside tool calls, leave result-producing calls unbound, or omit a save. Do not substitute hand-built dictionaries or redefined models for tool result objects.

## Represent flight legs separately
- Treat each explicitly described flight segment as its own search, using that leg’s origin, destination, and departure date. For a round trip, search outbound and return separately, reversing the route for the return; do not use an unsupported `return_date` argument or treat the return date as another outbound date. Apply an explicitly requested flight class to both directions; if directional results are already cached, retrieve and filter each direction.
- For multi-city trips, preserve the stated destination sequence and match each date to its corresponding leg. Do not combine dates or invent arrival dates.

## Validate tool arguments and preserve user intent
- Treat each tool’s declared argument list as a strict whitelist: validate every keyword against that tool before calling, use the full supported field name, and do not invent aliases. Match the field to the user’s meaning (for example, hotel stars use `stars`; a state or state abbreviation uses `state`, not `city`; a city uses `city`; a named attraction uses `attraction_name`; and amenities use declared fields such as `has_laundry_service` or `has_kids_club`, not shortened labels). Preserve user-provided entity values, labels, and identifiers verbatim—including airline codes, attraction-type terms, and state abbreviations—without autocorrecting, translating, or substituting guessed equivalents. For a newly requested hotel district or area within a city, use `neighborhood` when supported. If compatible cached hotel results exist, refine them with `filter_hotels` using those results as `prior_results`, and save the refinement under a new key; retrieving the cache alone does not satisfy the new constraint. Hotel searches require check-in and check-out dates, and hotel filters require `prior_results`.
- Carry forward relevant details from the conversation and include explicitly supplied criteria in the appropriate call. Send only schema-supported parameters; do not infer amenities, ratings, or other preferences. Do not infer exact party or room counts from broad descriptions such as “family.” Treat “solo” as one traveler only when a supported traveler-count field is available; do not infer a room count from it. A traveler count is not a flight-search parameter unless the schema provides one.
- When refining a cached result, do not resend criteria already represented in that result; apply the newly introduced preference with the appropriate filter.

## Proximity between travel domains
- Call `search_nearest` only when the user explicitly requests proximity between supported domains. Before calling it, verify that each cached result covers the specific requested target, not merely the same domain or city. For example, a generic city attraction search does not cover a separately named attraction; search for the named attraction using `attraction_name` unless the cache summary shows that exact target is already covered.
- Pass the relevant result objects for the two domains being compared. Set `groupBy` to the domain whose candidates the user wants ranked or recommended (the focal domain), not the reference domain: hotels near an attraction use `groupBy="hotel"`, while restaurants near a hotel use `groupBy="restaurant"`.
- Interest in visiting or dining at a place alone does not imply a proximity request or require a nearest-results call.

## Missing mandatory information
Before searching, match each required tool field to an explicit value in the full conversation; related context does not automatically satisfy that field. For example, a reunion date is not necessarily a flight departure date, and restaurant cuisine or budget does not supply the required restaurant city. Do not infer missing mandatory values or use defaults. If any are missing, make one `seek_information` call asking only for the missing mandatory information across the requested domains; optional preferences are not mandatory inputs.
