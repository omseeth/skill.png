# Travel Planning Skill

## Incremental planning and cache use

- Before emitting code, audit the planned calls against the latest turn and full conversation: for each new request or accepted preference, identify its intended item, domain, relation, and schema-supported argument, then verify that a planned call includes it. Do not reprocess unchanged domains. Use only a listed, compatible cache result for refinement; if none exists and mandatory inputs are available, search instead of filtering. After the audit, emit `print("No planning needed")` only when valid cached results already satisfy every requested action and constraint and no search, filter, sort, nearest-results call, or other planning operation was performed. Use only operations needed to satisfy the request; do not add sorting or other post-processing unless requested or necessary to fulfill a stated preference.
- Treat the latest user turn as an update to the trip plan. Check cache coverage separately for each requested domain and constraint, using relevant conversation context. For an affected domain, retrieve the latest relevant valid result with `get_results_from_cache(key="...")` into a local variable and pass it as `prior_results` when required. Apply only the newly introduced constraint to results that already represent earlier criteria; search when a needed result is unavailable. Do not redo unaffected domains or rely on variables from earlier executions.
- A cached base result does not satisfy a newly requested constraint, and a result for one domain does not satisfy a request for another. Use `print("No planning needed")` only when relevant, valid cached results already satisfy every requested action and constraint.
- Call the provided tools directly as functions; do not import the tools, modify module paths, or define or redefine tool functions or their models. For every required search, filter, sort, or nearest-results call, assign the exact return value to a variable and immediately save it with `save_to_cache` under a unique, descriptive key. Do this for every call, including each distinct leg or refinement; never leave a result-producing call bare or omit its save. Save refined results under a new key, and do not substitute hand-built dictionaries or redefined models for tool result objects.

## Represent flight legs separately
- Treat each explicitly described flight segment as its own search, using that leg’s origin, destination, and departure date. For a round trip, search outbound and return separately, reversing the route for the return; do not use an unsupported `return_date` argument or treat the return date as another outbound date. Apply an explicitly requested flight class to both directions; if directional results are already cached, retrieve and filter each direction.
- For multi-city trips, preserve the stated destination sequence and match each date to its corresponding leg. Do not combine dates or invent arrival dates.

## Validate tool arguments and preserve user intent
- Check each specific function’s schema for supported argument names, required fields, declared types, and cardinality; search and filter variants may support different fields. Use the exact field that matches the user’s meaning and do not invent aliases. Filters require a real, compatible `prior_results` object. For example, hotel star requirements use `stars`, a region belongs in `state`, a city in `city`, and a named attraction in `attraction_name`. Use the schema’s exact amenity field (such as `has_laundry_service`) when that preference is stated. Hotel searches require check-in and check-out dates, and hotel filters require `prior_results`. Do not pass a single airport value as a list unless the field is list-valued, and distinguish city-level requests from requests for a specific airport. Preserve explicit neighborhood labels in `neighborhood`. Encode an exact N-star hotel request as `stars=[N, N]` when the field represents a minimum/maximum pair.
- Carry forward relevant details from the conversation and include explicitly supplied criteria in the appropriate call. Send only schema-supported parameters; do not infer amenities, ratings, or other preferences. Do not infer exact party or room counts from broad descriptions such as “family.” Treat “solo” as one traveler only when a supported traveler-count field is available; do not infer a room count from it. A traveler count is not a flight-search parameter unless the schema provides one.
- Resolve terse or elliptical replies using the immediately preceding assistant prompt and full conversation before assigning values to tool fields; do not reinterpret a reply to a question about one field as a different preference. Preserve user-supplied names, abbreviations, and codes verbatim rather than expanding or substituting them. When only a state or region is supplied, including an abbreviation, use `state`, not `city`.
- Format time-window values exactly as the relevant tool schema and examples require. A cache summary may serialize a time differently from the tool’s accepted input format; convert explicit user times to the accepted format while preserving their meaning, and do not resend a time constraint already represented in the selected cached result.
- Map an allergy to a schema-supported allergy-option field only when the allergen is directly represented by that option; for example, a nightshade allergy can map to `has_tomato_allergy_options=True` because tomato is a nightshade. Do not substitute an unrelated allergen field or imply that a narrower option guarantees accommodation for the full allergy.
- When refining a cached result, retrieve the most refined compatible base that preserves all earlier active criteria and pass it as `prior_results`. Include every newly introduced, schema-supported criterion in the matching filter argument, but do not resend criteria already represented in the base. Retrieval alone is not refinement, and passing only `prior_results` is not sufficient. If no compatible base exists, search when mandatory inputs are available.

## Proximity between travel domains
- Call `search_nearest` only when the user explicitly requests proximity between supported domains. Before calling it, verify that each cached result covers the specific requested target, not merely the same domain or city. For example, a generic city attraction search does not cover a separately named attraction; search for the named attraction using `attraction_name` unless the cache summary shows that exact target is already covered.
- Pass the relevant result objects for the two domains being compared. Set `groupBy` to the domain whose candidates the user wants ranked or recommended (the focal domain), not the reference domain: hotels near an attraction use `groupBy="hotel"`, while restaurants near a hotel use `groupBy="restaurant"`.
- Interest in visiting or dining at a place alone does not imply a proximity request or require a nearest-results call.

## Missing mandatory information
Check required inputs separately for each requested action and domain against explicit values in the full conversation; related context does not automatically satisfy a required field. For example, a reunion date is not necessarily a flight departure date, and restaurant cuisine or budget does not supply the required restaurant city. Do not infer missing mandatory values or use defaults, except for the explicit hotel-date rule below. If any action lacks mandatory information, make one `seek_information` call asking only for those missing inputs. Do not search an incomplete action, but still execute and cache other requested actions whose own mandatory inputs are complete. Optional preferences are not mandatory inputs.

If a hotel stay is clearly at the single destination of an explicitly dated round trip and no separate hotel dates were given, use the outbound date as check-in and the return date as check-out. If the destination or date relationship is ambiguous, ask instead of inferring.
