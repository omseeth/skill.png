# Travel Planning Skill

## Cache-aware tool workflow
- At each turn, inspect cache summaries and identify which domains or itinerary legs the latest turn changes. For each changed request, retrieve by its exact key any cached result whose scope can cover the request, including a broader location or category result that can be narrowed with a filter. The cached result need not already contain a newly requested filterable criterion. Apply the matching `filter_*` tool with that result as `prior_results`, preserving constraints already embodied in it and adding every explicit new constraint in the appropriate field. Do not use a narrow result for a broader request, or reuse a result for a different domain, location, date, or leg. Run a new search only when no cached result can cover the changed request or its scope has changed such that the result is unsuitable; leave unaffected domains and legs alone.
- When the user requests proximity, use the relevant hotel and attraction or restaurant results with `search_nearest`. Set `groupBy` to the domain the user wants prioritized.

## Tool results and constraints
- Assign every search, filter, sort, and nearest-results output to a variable, then immediately save it with `save_to_cache` under a unique, descriptive key before using it in later calls. Pass the assigned prior result to filters, use distinct variables and keys for separate domains or legs, and do not overwrite valid cache entries unintentionally.
- Pass only criteria supported by the conversation, map each value to the field that expresses it, and preserve the user's entity text. For example, put a state abbreviation in `state`, not `city`. Use the tool's accepted format for preferences such as time ranges; use an example format only when supported by the tool. Distinguish hotel stars (`stars`) from guest ratings (`rating`); for a supported “at least N stars” constraint, use the inclusive range from N to the field's maximum, and for an exact category use the same value as both bounds. Do not add unrelated preferences.

## Flight itinerary legs

Use a date as a leg's `departure_date` only when the user explicitly connects it to that flight. A date given for a related event, such as a reunion or conference, is not by itself a flight departure date. If a requested leg's departure date is missing, ask for it rather than inferring or substituting another date.
Treat each explicitly described flight leg as a separate directional search with its own origin, destination, and `departure_date`. Unless the user specifies a one-way trip, interpret travel from a first date to a later date as a round trip: search outbound on the first date and return in the reverse direction on the second date, each in a separate call with its date as `departure_date`. Never encode the return as `arrival_date` on the outbound call, and do not assume unstated endpoints. Apply an explicitly requested flight class and other explicitly trip-wide flight preferences to both legs. Map any stated airport code to the corresponding origin or destination airport-code field. Handle each leg separately under the result-handling rule above.

## Required-argument checks
Before each tool call, verify that all of that tool's mandatory parameters are available from the full conversation and context. A hotel search requires a city, check-in date, and checkout date. If the user provides a check-in date and an explicit stay length in nights but no checkout date, call `adjust_date` with the check-in date and stated number of nights, then use its result. Do not infer checkout from vague timing such as “weekend,” or infer unspecified guest or room counts. If required details remain missing, use `seek_information` to ask only for those details; do not invent values, pass `None`, or make a partial call for that request. For requests spanning domains or legs, bundle missing mandatory details into one information request while proceeding with other fully specified requests when appropriate. Do not ask for optional preferences.
