# Travel Planning Skill

## Cache-aware tool workflow
- At each turn, inspect cache summaries and identify which domains or itinerary legs the latest turn changes. For each changed request, retrieve by exact key a compatible cached result for the same domain, location, dates, and leg whenever its candidate set can be narrowed to the request. It need not already include newly supplied filterable criteria such as cuisine, budget, rating, or amenities. Apply the matching `filter_*` tool to that result with the new constraints, retaining constraints already embodied in the cached result. Do not repeat a base search just to add filterable criteria. Search only when no compatible cached result exists or the request's scope has changed; leave unaffected domains and legs alone.
- Treat a request to stay “in” or “near” a named neighborhood or district as a hotel `neighborhood` constraint, not a `search_nearest` request. Do not use `search_nearest` as a substitute for an on-site hotel feature or amenity. Use it when the user wants proximity between two distinct domains (hotels, attractions, or restaurants): provide exactly two compatible result objects, one for each domain, and ensure one includes any named target (run a focused exact-name search if needed). For hotels near attractions, search for both hotels and the requested attraction category, then set `groupBy` to hotels. In other cases, set `groupBy` to the domain the user wants prioritized.

## Tool results and constraints

- Use exact supported field names when mapping criteria: hotel hot tubs and saunas map to `has_hot_tub=True` and `has_sauna=True`; a nightshade-allergy accommodation request maps to the supported restaurant field `has_tomato_allergy_options=True`. For a guest-rating floor, use `[N, 5]`; reserve equal bounds for explicitly exact ratings or categories.
- Assign every search, filter, sort, and nearest-results call to a variable and immediately save that same result with `save_to_cache` under a unique, descriptive key, even when it is the final call. For example, use `results = search_restaurants(...)` followed by `save_to_cache(key="restaurants", value=results)`. Do not call these tools inline, print their results instead of saving them, or save an assumed or differently named variable. Pass the assigned result to later filters or nearest calls, use distinct variables and keys for separate domains or legs, and do not overwrite valid cache entries unintentionally.
- Pass only criteria supported by the conversation, map each value to the field that expresses it, and preserve the user's entity text. For example, put a state abbreviation in `state`, not `city`. Check argument types against the tool schema: a single airport name or code is a scalar string (for example, `end_airport="ANC"`), not a one-item list. Use the tool's accepted format for preferences such as time ranges; use an example format only when supported by the tool. Distinguish hotel stars (`stars`) from guest ratings (`rating`): for “at least N stars,” use the inclusive range from N to the field's maximum; for an exact category, use equal bounds. For flight-time constraints, use the format accepted by the flight tool, such as 12-hour AM/PM strings. Do not copy a time verbatim from a cache summary if it is displayed in a different format; express an exact-time request with identical range endpoints and an “arrive by” request as a range from midnight to the stated time. Do not add unrelated preferences.
- Map explicit traveler descriptors to supported party-size fields when the count is unambiguous: for hotel searches, “solo” or “traveling alone” means `num_people=1`. Use stated party sizes directly, but do not infer an exact count from vague terms such as “family.”

## Flight itinerary legs

Do not infer a return leg or ask for a return date solely because the user mentions a vacation, getaway, or destination. Request a return date only when the user explicitly asks for a round trip or return leg, or supplies a return date.
Treat each explicitly described flight leg as a separate directional search with its own origin, destination, and departure date. For a round trip, search the outbound leg on the departure date and the return leg in the reverse direction on the return date; do not represent the return as `arrival_date` on the outbound search. Apply an explicitly requested flight class to both legs, and do not combine distinct legs by repeating keyword arguments in one call.

## Required-argument checks

For each flight leg, require a `departure_date` and at least one starting-airport identifier: `start_airport_city`, `start_airport`, or `start_airport_code`. Treat this conditional origin requirement as mandatory even though each field is individually optional; ask for any missing required detail before searching.
Before calling a travel tool, validate its mandatory parameters separately for each requested domain and itinerary leg using the full conversation and available context. If any are missing, do not call that incomplete tool or run a partial search; use one `seek_information` request listing only the missing mandatory details across incomplete requests. Continue with fully specified independent domains or legs, and save their results. Never invent values, pass `None`, or ask for optional preferences. For hotels, when the check-in date and an explicit stay length in nights are known but checkout is not, use `adjust_date` to calculate checkout. Do not infer a stay length; ask when a required date cannot be obtained or derived from explicit information.
