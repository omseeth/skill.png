# Travel Planning Skill

## Cache-aware tool workflow
- Reconstruct the current request from the full conversation, interpreting even a short reply in the context of the preceding assistant question. Identify only the changed domains or itinerary legs. For each changed request, inspect cache summaries and retrieve by exact key the most refined compatible result for the same domain, location, dates, and leg whose scope still covers the current request and its active constraints. Apply the matching `filter_*` tool only for genuinely new supported criteria, retaining constraints already embodied in the result. Do not repeat a base search just to add filterable criteria or regenerate unaffected domains or legs. If a follow-up adds no new supported constraint (including a reply declining further preferences), do not rerun or filter the search; if the user still wants the existing recommendations, retrieve the compatible cached result by its exact key. Search only when no compatible result can cover the request or its scope has changed.
- When the user requests proximity between domains, pass the relevant hotel and attraction or restaurant results to `search_nearest`, reusing compatible cached results rather than searching again solely to compute proximity. If the user names a specific attraction, restaurant, or hotel as the proximity target, ensure the results passed to `search_nearest` are scoped to or demonstrably include that named entity; a general city- or category-level result is not sufficient evidence. If needed, run a focused search using the exact name in the appropriate name field, assign and cache its result, and reuse any already-compatible result from the other domain. Set `groupBy` to the type of entity the user wants recommendations grouped around, not merely the location anchor: for example, restaurants near a hotel means `groupBy="restaurant"`, while hotels near attractions means `groupBy="hotel"`.

## Tool results and constraints
- Assign every search, filter, sort, and nearest-results call to a variable and immediately save that same result with `save_to_cache` under a unique, descriptive key, even when it is the final call. For example, use `results = search_restaurants(...)` followed by `save_to_cache(key="restaurants", value=results)`. Do not call these tools inline, print their results instead of saving them, or save an assumed or differently named variable. Pass the assigned result to later filters or nearest calls, use distinct variables and keys for separate domains or legs, and do not overwrite valid cache entries unintentionally.
- Pass only criteria supported by the conversation, map each value to the field that expresses it, and preserve the user's entity text. For example, put a state abbreviation in `state`, not `city`. Use the tool's accepted format for preferences such as time ranges; use an example format only when supported by the tool. Distinguish hotel stars (`stars`) from guest ratings (`rating`); for a supported “at least N stars” constraint, use the inclusive range from N to the field's maximum, and for an exact category use the same value as both bounds. Do not add unrelated preferences.
- Map explicit traveler descriptors to supported party-size fields when the count is unambiguous: for hotel searches, “solo” or “traveling alone” means `num_people=1`. Use stated party sizes directly, but do not infer an exact count from vague terms such as “family.”

## Flight itinerary legs

Use a date as a leg's `departure_date` only when it is explicitly linked to that flight leg. A date given for a destination event, such as a reunion, does not by itself establish the flight's departure date. Arrival-time constraints do not replace a missing departure date; ask for the departure date rather than inferring it.

Do not infer a return leg or ask for a return date solely because the user mentions a vacation, getaway, or destination. Request a return date only when the user explicitly asks for a round trip or return leg, or supplies a return date.
Treat each explicitly described flight leg as a separate directional search with its own origin, destination, and departure date. For a round trip, search the outbound leg on the departure date and the return leg in the reverse direction on the return date; do not represent the return as `arrival_date` on the outbound search. Apply an explicitly requested flight class to both legs, and do not combine distinct legs by repeating keyword arguments in one call.

## Required-argument checks
Before calling a travel tool, validate its mandatory parameters separately for each requested domain and itinerary leg using the full conversation and available context. If any are missing, do not call that incomplete tool or run a partial search; use one `seek_information` request listing only the missing mandatory details across incomplete requests. Continue with fully specified independent domains or legs, and save their results. Never invent values, pass `None`, or ask for optional preferences. Hotel searches require a city, check-in date, and checkout date. Use actual dates supplied or derived from explicit information, never example, current, or placeholder dates. Reuse explicit dates already established for the same trip as the hotel check-in and checkout dates when they identify the stay and the user has not supplied separate hotel dates. When check-in and an explicit stay length in nights are known but checkout is not, use `adjust_date` to calculate checkout. Do not infer a stay length; ask for any required date that cannot be obtained or derived from explicit information.
