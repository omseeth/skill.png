# Travel Planning Skill

## Cache-aware tool workflow
- At each turn, inspect cache summaries and identify which domains or itinerary legs the latest turn changes. For each changed request, retrieve by exact key the most refined cached result that matches the domain, location, dates or leg, and constraints, then apply the matching `filter_*` tool with only the newly supplied constraints. A cached result is suitable only when its original query scope can cover the current request: do not use a narrow named-item result for a newly broad category request, or a broad-category result when the user now requests a specific item; do not carry earlier entity constraints into a distinct request unless reaffirmed. If no suitable result exists, make a focused search for the missing request. Apply trip-wide preferences to every relevant cached result or itinerary leg, and leave unaffected domains alone rather than repeating valid searches.
- When the user requests proximity, use the relevant hotel and attraction or restaurant results with `search_nearest`. Set `groupBy` to the domain the user wants prioritized.

## Tool results and constraints
- Assign every search, filter, sort, and nearest-results output to a variable, then immediately save it with `save_to_cache` under a unique, descriptive key before using it in later calls. Pass the assigned prior result to filters, use distinct variables and keys for separate domains or legs, and do not overwrite valid cache entries unintentionally.
- Pass only criteria supported by the conversation, map each value to the field that expresses it, and preserve the user's entity text. For example, put a state abbreviation in `state`, not `city`. Use the tool's accepted format for preferences such as time ranges; use an example format only when supported by the tool. Distinguish hotel stars (`stars`) from guest ratings (`rating`); for a supported “at least N stars” constraint, use the inclusive range from N to the field's maximum, and for an exact category use the same value as both bounds. Do not add unrelated preferences.

## Flight itinerary legs
Treat each explicitly described flight leg as its own directional search with its own origin, destination, and `departure_date`. For a round trip or stated outbound/return date range, make a separate outbound search from origin to destination on the first date and a return search from destination to origin using the return date as that call's `departure_date`. Never encode the return as `arrival_date` on the outbound call or assume an origin or destination that the user has not stated. Apply an explicitly requested flight class to both legs, and do not combine distinct legs by repeating keyword arguments in one call. On follow-up turns, filter each cached leg affected by a trip-wide preference, including the return leg unless the user makes the preference leg-specific. For flight-time constraints, use a format accepted by the tool (for example, `12:00 PM`, not an unvalidated `HH:MM:SS` string); translate broad preferences such as “afternoon” into a bounded interval using the accepted format.

## Required-argument checks

- For hotel searches, require actual check-in and checkout dates; for flights, require an actual departure date for each leg, including the return leg of a round trip. Treat vague timing such as “last-minute” as missing date information, not as a date value.
- Omit unspecified optional arguments rather than passing `None` placeholders.
Before calling a travel tool, check its required parameters against the full conversation and available context. If any required details are missing, use `seek_information` to ask only for those details; do not invent values, pass `None`, or run a partial search. For requests spanning multiple domains, bundle missing required details for all requested domains into the same information request. Do not ask for optional preferences.
