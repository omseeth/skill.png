# Travel Planning Skill

## Learned rules

- **Use runtime tools directly and follow their schemas:** Tools, cache functions, and result models are provided by the runtime. Do not import libraries, redefine models or schemas, or add helper code. Use only supported arguments with the required types, pass list-valued fields as lists, and use keyword arguments except for `seek_information`. Write every result-producing search, filter, sort, or `search_nearest` call in two steps: assign its returned result to a variable, then save that exact, complete result object with `save_to_cache` under a fresh, descriptive key. Do not extract `.search_results`, rebuild, or merge tool output before saving. Use distinct keys for separate domains, itinerary legs, and updated results; never leave a result-producing call bare or omit its save. Retrieve cached results by assigning `get_results_from_cache(...)` to a variable before passing them to another tool; do not nest the retrieval call. Before emitting code, audit that each intended operation is assigned and saved, and avoid duplicate calls for the same intended operation. Do not pass unsupported parameters, such as traveler counts to flight tools, or invent optional criteria.

- **Combine known criteria on initial searches:** When no suitable cached base exists and multiple explicit criteria for one domain are already known, include them in the same search call where supported (for example, attraction type and name) rather than searching broadly and then filtering or repeating the search. For a hotel search, map any explicitly stated party size to `num_people` (for example, “solo” means `num_people=1`); apply a newly supplied count with a same-domain filter on a suitable cached hotel result when needed. Do not infer unspoken counts or pass traveler counts to flight tools.
- **Honor the user's request and values:** Use only explicitly requested domains; do not infer extra searches, preferences, amenities, or substitute similar categories. Do not map vague amenity wording to a narrower tool flag without clear equivalence. Preserve complete names, categories, criteria, and date strings unless a tool requires a format conversion. Map cities to `city`, states or regions to `state`, neighborhoods to `neighborhood` while retaining the full provided name, and airport codes to the corresponding airport-code field; do not put a state abbreviation in `city` or truncate a location value. When a domain is newly requested during an ongoing trip, use the already-established destination as its location when that context clearly applies rather than asking for a city already known. Check required inputs independently by domain: seek missing information, but proceed with other requested searches whose inputs are available. For ratings, treat a single numeric rating without minimum or “at least” language as exact `[x, x]`; “exactly x” is `[x, x]`, and an explicit “at least x” request is `[x, 5]`.

For a location combining a neighborhood or district with its city (for example, Midtown Atlanta or Downtown St. Louis), use the city in `city` and the full provided area phrase in `neighborhood`. When only a state or region is given, including an abbreviation, use `state`, not `city`.
- **Handle follow-ups incrementally through the cache:** Treat a short answer to an assistant's clarification question as an explicit user-provided value or preference; an affirmative answer accepting an offered domain or option is a request to proceed. On each turn, reconcile the full conversation and cache, including explicitly requested tasks still pending from earlier turns, then decide separately for every requested or clearly pending domain. If a suitable cached base exists and a new constraint is not reflected in it, retrieve the latest suitable result using `get_results_from_cache(key="<exact key from the cache summary>")` and assign the returned result; do not rely on variables from earlier code or turns. Apply only the new same-domain filter and save the update under a fresh relevant key. If no suitable base exists and required inputs are available, search and save. If required inputs are missing, ask for them while still completing other requested domains whose required inputs are available. A result summary satisfies a request only when it reflects all current constraints. For updates affecting multiple results, such as outbound and return legs, retrieve, filter, and process each independently. Do not repeat completed work, reapply constraints, or touch unrelated results. Never return no-planning merely because a cache entry exists. Compare the cache summary with the current conversation and follow the cache-update, search, or missing-input rules above for any unmet request or pending deliverable. Return no-planning only when every requested or pending deliverable reflects all current constraints and the latest turn adds no request, accepted offer, or new constraint.
- **Use proximity tools only for proximity requests:** Search for a named attraction when requested. Use `search_nearest` only when the user asks about proximity, with relevant domain results and `groupBy` set to the requested anchor domain. A request for a hotel or restaurant “near” a named attraction or landmark is a proximity request: retrieve the attraction results from cache or search for them if absent, then use them with the hotel or restaurant results. Do not pass the attraction name as a `neighborhood` value or approximate proximity with a neighborhood filter. A new neighborhood or area preference is a location constraint, not by itself a request to run `search_nearest`: apply and save same-domain filters to each explicitly targeted domain independently, using the latest suitable cached result for each, including a combined nearest result when it is a suitable filter base. If the user says the area applies to both hotels and restaurants, update both. If a later constraint changes an underlying domain result used by a proximity result, refresh and save `search_nearest` using the updated result and the latest suitable cached result for the other domain. If the latest suitable cached base is already the combined nearest result and supports applying the new constraint directly, filter and save it instead of making an unnecessary nearest call.
- **Search round-trip flights as separate legs:** For an explicit round trip or date range with a return date, search outbound on the first date and return from destination to origin on the return date. Use each date only as that leg's `departure_date`; do not put the return date in the outbound `arrival_date` unless the user separately states an outbound arrival-date constraint. Cache each leg separately. Do not infer a return flight from hotel stay duration. When a requested flight is explicitly nonstop or non-stop, pass `num_layovers=[0]` on each applicable leg. If the user says the trip is one-way or declines a return flight, search only outbound.
- **Format flight time ranges as required:** For `departure_time` and `arrival_time`, use the validator's accepted 12-hour format with AM/PM (for example, `12:00 PM`), not `HH:MM:SS`. Choose a supported interval for vague time periods.

- For a one-sided flight-time bound, complete the range to the day boundary: “before X” uses `["12:00 AM", X]`, and “after X” uses `[X, "11:59 PM"]`, preserving the stated AM/PM value.

- **Distinguish required dates from optional details when seeking information:** `search_flights` requires `departure_date`; `arrival_date` is optional, even for a round trip. `search_hotels` requires both `checkin_date` and `checkout_date`, while `num_people` and `num_rooms` are optional. Phrases such as “last-minute,” “weekend getaway,” or “family vacation” do not provide exact travel dates. Do not infer or substitute sample dates; ask only for missing required values, not optional counts or dates.

- **Check required city inputs and distinguish event dates from travel dates:** `search_hotels` and `search_restaurants` require `city`. When lodging is requested for an explicitly planned trip and both trip dates are known, use the trip start and end dates as hotel check-in and check-out. When an explicit trip start date and number of hotel nights are known, use the start date as check-in and call `adjust_date` with the night count to compute checkout. For a hotel added to an ongoing itinerary, reuse a clearly established trip date as check-in when applicable; do not guess check-in by subtracting a day from checkout. If a required hotel date cannot be established from user-provided itinerary details, seek it. Pass user-provided date strings unchanged to date-taking tools unless the schema explicitly requires a different format; do not parse, reformat, or calculate dates in Python or import date libraries. Use `adjust_date` only to compute checkout from an explicit trip start date and stated number of hotel nights. Never infer a one-night stay or derive check-in by subtracting from checkout; use explicitly supplied stay boundaries or a clearly established itinerary start date, and seek any genuinely missing required date. A date given only for an event, such as a wedding or reunion, is not a flight departure date or hotel stay date unless the user explicitly identifies it as travel timing.

- **Map multi-city lodging to intended overnight stops:** When a user requests hotels in cities on a multi-leg route, search the explicitly intended lodging destinations or overnight stops; do not automatically include a departure-only origin as a hotel city. Do not infer per-city stay lengths or dates from flight legs. Use only established trip dates, and seek information if a required hotel input cannot be determined.

- **Resolve accepted offers against cache criteria:** Treat an affirmative reply accepting an earlier offer as a request to complete that specific deliverable. A cached result satisfies the offer only if it matches the requested location, category, and other criteria; a same-domain result for a different attraction, cuisine, or filter is not sufficient. If a suitable result is cached, retrieve the latest one even when no search or filter is needed. Otherwise, use a suitable cached base with the needed same-domain filter, or search if no suitable base exists and required inputs are available. Ask for missing required inputs, and do not repeat completed work or redo an unrelated domain whose result already reflects current constraints.

- **Resolve follow-ups about assistant-suggested places or options:** If the assistant names a specific area, attraction, or other travel option and the user asks what is there or available, asks for details, or accepts exploring it, treat that as a request to explore the referent. For a named area or neighborhood, retrieve and assign the latest suitable result for the relevant domain, apply a same-domain `neighborhood` filter using the full area phrase, and save the filtered result under a fresh key. This is a location request, not a proximity request; do not call `search_nearest`. For other suggested places or options, retrieve the latest suitable result and apply the corresponding same-domain filter when needed. Use `search_nearest` only for an explicit proximity request.

- **Clarify trip context without a planning request:** If the user provides trip context without clearly requesting a planning service, ask what assistance they want.

- **Interpret clarification answers in context:** Map a short answer to the field or fields the assistant asked about, rather than interpreting an ambiguous word or abbreviation in isolation. If the reply supplies multiple criteria for one domain, capture all of them and include them together in the same follow-up filter call where supported; do not select only one criterion.

Treat each follow-up as a delta to the latest suitable cached result: identify the exact base, the new constraint, and the requested deliverable. When a short reply accepts a specific offer or supplies a value, apply that value to the matching result and save the filtered object under a fresh key—for example, an accepted balcony option requires `has_balcony=True`, and “There are 3 of us” requires `num_people=3`. Do not satisfy a follow-up by merely retrieving or re-saving an unchanged result, and do not declare no-planning while a requested constraint remains unapplied. Do not carry forward an assistant-suggested criterion unless the reply clearly accepts it.

Use tool enum values with their exact schema casing: flight class is `['first']`, not `['First']`. Interpret a preference in its own domain: first class modifies flights, not hotel stars. Do not add hotel searches, filters, or sorting when the user only updates flight preferences, and do not sort results unless requested or necessary for the deliverable.

Distinguish an area from a proximity relationship: “near Downtown St. Louis” naming the desired area is a neighborhood filter, not a nearest search. Call `search_nearest` only for a requested relationship between two distinct result domains or anchors. Before calling it, retrieve and assign each suitable cached input, pass exactly two supported domain inputs once each (for example, hotels and attractions), and set `groupBy` to the requested target. Assign and save the exact nearest result; never call it with only hotels or with attractions supplied twice. Map a state abbreviation such as NV to `state`, not `city`.

For a multi-domain request, make a compact deliverable ledger and perform only the needed operation for each item. Combine already-known criteria for the same domain in one initial search—for example, attraction type and attraction name—and reuse a suitable cached base instead of repeating a search. Before submitting, check that each intended operation appears once, each cached input is assigned before use, and every search, filter, sort, or nearest result is assigned and saved exactly as returned.
