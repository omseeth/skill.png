# Travel Planning Skill

## Learned rules

- **Use runtime tools directly and follow their schemas:** Tools, cache functions, and result models are provided by the runtime. Do not import libraries, redefine models or schemas, or add helper code. Use only supported arguments with the required types, pass list-valued fields as lists, and use keyword arguments except for `seek_information`. Treat every result-producing call—search, filter, sort, or `search_nearest`—as a paired operation: assign its result to a variable and save that exact result with `save_to_cache` under a fresh, descriptive key. Use distinct keys for separate domains, itinerary legs, and updated results. Before finalizing, verify that every produced result has been saved. Do not add result printing, summaries, or diagnostic output unless requested, and avoid unrelated cache reads. Tool outputs are typed result models, not dictionaries: pass them directly to subsequent tools and cache functions; do not subscript them. If inspection is genuinely needed, use declared model attributes. Do not pass unsupported parameters, such as traveler counts to flight tools, or invent optional criteria.

- **Combine known criteria on initial searches:** When no suitable cached base exists and multiple explicit criteria for one domain are already known, include them in the same search call where supported (for example, attraction type and name) rather than searching broadly and then filtering or repeating the search. A clearly stated party size such as “solo” is an explicit count; pass `num_people=1` for a hotel search. Do not infer unspoken counts.
- **Honor the user's request and values:** Use only explicitly requested domains; do not infer extra searches, preferences, amenities, or substitute similar categories. Do not map vague amenity wording to a narrower tool flag without clear equivalence. Preserve complete names, categories, criteria, and date strings unless a tool requires a format conversion. Map cities to `city`, states or regions to `state`, neighborhoods to `neighborhood` while retaining the full provided name, and airport codes to the corresponding airport-code field; do not put a state abbreviation in `city` or truncate a location value. When a domain is newly requested during an ongoing trip, use the already-established destination as its location when that context clearly applies rather than asking for a city already known. Check required inputs independently by domain: seek missing information, but proceed with other requested searches whose inputs are available. For numeric `rating` requests, a bare single value is exact `[x, x]` unless the user says “at least” or otherwise clearly requests a threshold, which is `[x, 5]`. Phrases such as “an x-star rating” or “rated x stars” without “exactly” mean a minimum `[x, 5]`; “exactly x” means `[x, x]`. Preserve explicit ranges.
- **Handle follow-ups incrementally through the cache:** On each turn, reconcile the full conversation and cache, including explicitly requested tasks still pending from earlier turns. Use the cache summary to identify the latest suitable base for each affected result, then retrieve it with `get_results_from_cache(key="<exact key from the cache summary>")` and assign the returned result; do not rely on variables from earlier code or turns. Apply only newly stated or changed constraints not already reflected in the base, using the appropriate same-domain filter. A broad search summary that does not reflect a new constraint does not satisfy it. If an update applies to multiple cached results, such as outbound and return flight legs, retrieve, filter, and process each independently. Do not mix domains, repeat already-applied constraints, rerun completed work, or touch unrelated results. Search afresh only when no suitable cached base exists; do nothing only when the cached results satisfy all current constraints. Save each updated result under a relevant fresh key, following the persistence rule.
- **Use proximity tools only for proximity requests:** Search for a named attraction when requested. Use `search_nearest` only when the user asks about proximity, with relevant domain results and `groupBy` set to the requested anchor domain. Do not approximate proximity by extracting a neighborhood and using it as a filter.
- **Search round-trip flights as separate legs:** Search a return leg when the user explicitly requests a round trip or return flight, or provides a travel date range that establishes a return date. Search outbound from origin to destination on the first date, then return from destination to origin on the return date, using that date as the return leg's `departure_date`. Cache each leg separately. Do not infer a return flight from hotel stay duration alone, and do not use the return date as the outbound `arrival_date` unless the user explicitly states it as an arrival-date constraint. If the user says the trip is one-way or explicitly declines a return flight, search only the outbound leg.
- **Format flight time ranges as required:** For `departure_time` and `arrival_time`, use the validator's accepted 12-hour format with AM/PM (for example, `12:00 PM`), not `HH:MM:SS`. Choose a supported interval for vague time periods.

- **Disambiguate flight preferences and require an origin:** When replying to a question about airline or class, interpret a short uppercase code-like token as an airline (for example, `airline=["AM"]`), not a morning time preference; interpret it as a time only when context clearly refers to time of day. Use the lowercase flight-class values `economy`, `business`, or `first`. A flight search requires both a departure date and an origin in a supported origin field. A known hotel city or destination does not establish the origin; ask for any missing required origin rather than inventing a route.

- **Distinguish required dates from optional details when seeking information:** `search_flights` requires `departure_date`; `arrival_date` is optional, even for a round trip. `search_hotels` requires both `checkin_date` and `checkout_date`, while `num_people` and `num_rooms` are optional. Phrases such as “last-minute,” “weekend getaway,” or “family vacation” do not provide exact travel dates. Do not infer or substitute sample dates; ask only for missing required values, not optional counts or dates.

When multiple requested domains are blocked by missing required inputs, ask for all those missing values in one clarification, while proceeding with any other requested domains whose required inputs are available.

- **Check required city inputs and distinguish event dates from travel dates:** `search_hotels` and `search_restaurants` require `city`. When lodging is requested for an explicitly planned trip and both trip dates are known, use the trip start and end dates as hotel check-in and check-out. When an explicit trip start date and number of hotel nights are known, use the start date as check-in and call `adjust_date` with the night count to compute checkout. For a hotel added to an ongoing itinerary, reuse a clearly established trip date as check-in when applicable; do not guess check-in by subtracting a day from checkout. If a required hotel date cannot be established from user-provided itinerary details, seek it. Preserve user-provided date strings unless conversion is required, and use `adjust_date` rather than importing date libraries or doing date arithmetic in Python. A date given only for an event, such as a wedding or reunion, is not a flight departure date or hotel stay date unless the user explicitly identifies it as travel timing.

- **Map multi-city lodging to intended overnight stops:** When a user requests hotels in cities on a multi-leg route, search the explicitly intended lodging destinations or overnight stops; do not automatically include a departure-only origin as a hotel city. Do not infer per-city stay lengths or dates from flight legs. Use only established trip dates, and seek information if a required hotel input cannot be determined.

- **Retrieve accepted pending offers from cache:** Treat an affirmative reply that accepts an earlier offer to provide recommendations or results as a request to deliver them. Retrieve the relevant latest cached result, even if no new search or filter is needed; use the no-planning response only when there is no pending deliverable.

- **Resolve follow-ups about assistant-suggested places or options:** If the assistant names a specific area, attraction, or other travel option and the user asks what is there or available, or asks for details, treat the response as a request to explore that referent when the user is clearly taking up the suggestion. Retrieve the latest suitable cached result and apply the corresponding same-domain filter when needed. Use `search_nearest` only if the user requests proximity.

- **Clarify trip context without a planning request:** If the user provides trip context without clearly requesting a planning service, ask what assistance they want.
