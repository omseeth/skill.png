# Tool Calling Skill

## Select endpoints and map requests to documented parameters
- Identify the requested outputs and scope before choosing tools. Similar topics do not make endpoints interchangeable: listings differ from autocomplete suggestions, current conditions differ from forecasts, and counts for different administrative levels are distinct. Likewise, one email-related result (such as validity) does not automatically provide MX, SMTP, or disposable status. Use an endpoint only when its documented function and outputs cover the requested result; otherwise make separate calls for each distinct output. Do not repurpose a related endpoint or parameter to approximate an operation its documentation does not support.
- Translate explicit constraints into the corresponding documented parameters, including forecast horizon, result count, page, sort order, date type, and search filters. Use the endpoint's accepted parameter names, types, enum values, codes, and casing; do not borrow them from a similar endpoint.
- Translate directly implied context into supported values when the mapping is clear: a named choice may map to its canonical selector, a request for a single result may imply a count of one, and an unambiguous country or locale may imply supported language, store, size-system, or unit settings. Include such values only when the request directly entails them or documentation specifies a needed default. Do not guess opaque identifiers, coordinates, or unsupported settings.
- When multiple pages are requested, call every requested page, including the first. Set the documented page and page-size parameters on each call and carry shared filters across pages; do not assume a single page retrieves the full collection.
