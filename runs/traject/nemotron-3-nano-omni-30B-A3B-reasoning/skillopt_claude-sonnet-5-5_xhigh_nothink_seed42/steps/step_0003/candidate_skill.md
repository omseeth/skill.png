# Tool Calling Skill

## 1. Output format (a malformed call scores zero)
- `tool name` is the tool's `### ` heading copied character-for-character, in the form `Provider: API` (colon + space), including any suffix or symbol such as `?{parameters}`, `{artist}`, `/v1/weather`, `(New)`. Never trim, tidy, shorten, drop the provider prefix, or use ' — ' or '-'. Example: `BestBuy Product Data: BestBuyProductData`, not `BestBuy ProductData`; `Arabic news API: CNN Arabic`, not `CNN Arabic`.
- Every call object has all three keys: `tool name`, `required parameters`, `optional parameters`. Use `[]` when a list is empty; never omit a key.
- Each parameter is an object `{"name": "x", "value": "y"}`. Never emit bare names like `["criteria"]`. Every value is a quoted JSON string, including numbers and booleans (`"5"`, `"-118.49"`, `"true"`).
- Output ONE flat, bracket-balanced JSON list inside `<answer>...</answer>`. Always close it with `]` and the `</answer>` tag.

## 2. Cover every clause (stopping early is the most common failure)
- Before answering, write a short numbered checklist with one line per action in the query: every sentence, every then/also/next/finally clause, every list item ('pricing, reviews, similar items' = 3), every named platform or provider, and every narrated past-tense step ('they retrieved...', 'they searched...'). Hedges like 'possibly' do not make an item optional. Each item needs its own call, so the call count must be at least the checklist length.
- Re-read the FIRST and LAST sentences before finalizing. Opening searches and the final clause are the parts most often dropped. Long queries often need 7-10 calls.
- If a tool takes one value and the query names N entities (emails, SKUs, domains, cities, pages, search terms), make N calls.
- Different wordings usually map to different sibling endpoints of one provider, and each needs its own call (e.g. kanji by strokes / by grade / by radical / by meaning; drawing cards vs rolling dice; MX records vs disposable check vs SMTP vs format validation). Do not substitute one endpoint for a sibling.
- If a clause names a provider or outlet, cover it with that provider's endpoint. If none exists, use the general by-source tool with the outlet as the source parameter. Never skip the clause.
- Do not call two tools for one thing. If one endpoint already covers the whole phrase, call it once.

## 3. Tool selection
- Match each clause's key noun, verb, scope and provider literally to a tool's name and description, preferring the dedicated endpoint over a broader generic one. 'Country data' -> 'Data of countries', not airport or route data. 'Current conditions' / 'active alerts' -> the tool with that name. 'Specific flight searches' / 'detailed info about flight X' -> that provider's flightSearch / flightInfo tools. A named provider ('Flightera', 'Priceline', 'OpenCritic', 'Pokédex') -> that provider's endpoint, never another game's or service's tool.
- When several tools could serve a clause, prefer the one whose parameter names mirror the query's inputs. Latitude/longitude given -> the tool whose *required* params are latitude/longitude, not a generic tool where lat/lon are optional extras.
- Distinguish siblings by quantity and input type: several dice with a side count -> the plural/custom dice tool with `dice` and `sides`; one die -> the singular tool; several cards -> 'Cards'; one card -> 'Card'. A bare domain needs a domain-level tool, a full email needs an email-level tool (if a tool takes `username` and `domain` separately, split the email), and a product or SKU ID needs a by-ID/detail tool.
- When a query lists separate checks on one subject (disposable, format validity, MX, SMTP, role account), use one dedicated tool per named check, preferring a tool whose description literally names that check. For 'comprehensive' checks, include each distinct tool covering a different check. Do not stack several tools on the same single check.
- Every call must trace to a clause. Do not add unrelated helper, status, bulk-generator, create/delete/submit or auth tools when the query only asks for a lookup, and never invent a value (player name, id, email) to fill a required parameter.

## 4. Parameters
- Use ONLY parameter names in the chosen tool's schema, and put each one in the list where the schema puts it. Names under 'Required parameters' go in `required parameters`, even range-style fields (`start`/`end`, `interval`) that seem optional. Names under 'Optional parameters' go in `optional parameters`, even when they carry the query's main input (id, `q`, `title`, `criteria`, `text`). Never put one parameter in both lists, and never borrow a parameter from a sibling tool.
- Fill a value for every required parameter. Copy IDs, SKUs, URLs, emails, domains, names, tickers, flight numbers, search keywords and Bible verses verbatim from the query. If the query names a value for a function/type/endpoint-style field (e.g. `DIGITAL_CURRENCY_DAILY`), use it exactly. Never substitute an invented one.
- Map every constraint the query states or clearly implies to the tool's matching parameter. Examples: 'page 1' -> page, '20 per page' -> pageSize, '10 matches' -> limit, '4 dice with 10 sides' -> dice and sides, '3 times' -> rolls, 'draw 5 cards' -> pulls, 'minimum length 5' -> minLength, 'most helpful' -> HELPFUL, 'with a demo key' -> key `demo`. If the tool has a companion mode parameter (e.g. themesType `ALL` when all themes are required), set it too. Put a search subject in the query/criteria field using the query's own words.
- Do NOT add optional parameters the query neither states nor implies (units, locales, currencies, sort orders, format flags, default pages). Never emit empty or placeholder values. Never repeat a parameter name within one call. Join multiple values into one value, comma-separated, or in the array form the schema suggests.
- Codes and enums: when the schema lists options or shows a format, copy that exact form. When a category/topic/country field gives only a loose hint (e.g. 'country code like US, CA'), that hint is an example, not an enum. Use lowercase there (`business`, `us`, `uk`).
- Dates are `YYYY-MM-DD`. A range such as 'January 1-31, 2024' fills both the from and to fields (`2024-01-01`, `2024-01-31`).
