# Tool Calling Skill

## Learned rules

- **Map each requested deliverable to the endpoint that performs it.** Break a multi-part query into distinct requested outputs or facets, recording each subject and its constraints before choosing endpoints; keep each clause's values attached to the entity it describes. Choose the most directly fitting documented endpoint using its exact `Provider: endpoint` name. For a broad request, prefer a documented broad or all-scope endpoint when it fully provides the requested output; do not choose a narrower endpoint merely because it has fewer required arguments. Conversely, cover separately requested outputs when they require distinct endpoints rather than assuming one broad or multi-capability lookup covers every facet. For each candidate, verify that its result fulfills the requested action for the right entity and scope: suggestions, checks of weaker properties, or unfiltered results do not substitute for a requested lookup, verification, or scoped result. Keep only calls that cover distinct requested results; reject speculative, duplicate, or adjacent calls, and candidates whose schemas cannot express the requested target without misusing fields or inventing arguments. Do not fan out across generic tools or marketplaces merely because the user did not specify a source. Use a fallback only when it genuinely satisfies the action; do not choose a contradictory endpoint or add unrelated calls merely because they share a topic.

Construct that identifier by copying the tool's concise `Provider:` value and `API:` endpoint value verbatim, joined as `Provider: API`; do not use the provider's descriptive blurb, the endpoint label alone, or a synthesized title, and verify the final identifier matches a listed tool exactly. Before treating a requested facet as unsupported because no dedicated endpoint exists, check whether a documented configurable endpoint can perform it through an operation or function selector. Use the matching selector only when its value is established by the endpoint documentation or a standard, well-known value for that API; do not guess unsupported selectors or use an unrelated operation just to claim coverage.
- **Scope and bundle calls appropriately.** Make separate calls for distinct targets, checks, or purposes when they require distinct arguments. Combine multiple filters or categories in one call when they concern the same operation and the endpoint supports that syntax. Do not repeat a check, add overlapping searches, or introduce unrequested calls.

For multi-value filters, preserve whether the user asks for any listed value or for all of them to match. Use the endpoint's documented list encoding and, when available, its documented match-mode parameter; do not assume comma-separated values or an all-match mode without schema support.

- **Handle independent calls, pagination, and explicit sorting requests.** Issue calls for independent required operations together rather than waiting for one to finish when the tool interface supports it. When the user explicitly requests the first page, pass `page=1` on every applicable paginated call; do the same where applicable when a requested count is served by a paginated endpoint. When the user requests multiple pages or more results from a collection already queried, use distinct sequential page values and retain any requested page size rather than repeating the first page by default. If the user explicitly requests default sorting and the endpoint exposes a documented default-sort value, use that value; do not guess or add unrelated parameters.
- **Build arguments from the endpoint schema.** Use exact parameter names, satisfy the schema's semantic types, include every required parameter, and put parameters in the required or optional group specified by the tool. Carry every explicit or clearly implied constraint into its matching documented field, including optional qualifiers such as location or area, active status, locale, sort, postal code, duration, quantity, source, or output mode; a broader or unfiltered response is not a substitute when the endpoint supports the requested scope. Include optional fields only when requested or clearly implied, not as speculative defaults. Map a requested count to the documented count field or `per_page`/`limit`; when the user asks for one result and the endpoint has a count field, set it to 1. If no count is requested, use the smallest conventional value needed. Preserve query values and their entity associations, converting them only to documented formats such as API codes, list syntax, or canonical enum spelling. Match the representation expected by each field: use a canonical slug when the schema requires one and convert quantities to documented units (for example, 5 minutes to 300 seconds). Serialize values according to the required call-format convention: follow explicit examples that consistently encode values as strings, even for numeric or boolean parameters; otherwise follow the declared schema types. Never invent enum tokens, identifiers, credentials, or empty placeholders. When a request specifies a market or locale, populate directly corresponding documented parameters (such as country, store, currency, or language) when their values are documented or unambiguously implied; use canonical codes and a market-specific locale when a documented mapping establishes one. For multiple markets, make a separate call per market and keep each market's settings together. Include related regional settings when the endpoint exposes a corresponding selector and an explicit market has a standard, unambiguous mapping to it: reuse the canonical market code for market/store/size-schema selectors when the API convention uses that code, and use the standard market locale for a language selector (for example, US -> en-US). This can be done without a separate reference lookup endpoint; do not invent opaque identifiers or guess nonstandard mappings. Infer locale-specific units or currency only when the user's geography, including an explicitly requested market, unambiguously implies one and the schema documents the exact value; otherwise omit them rather than guess. **Map administrative locations by hierarchy, not by label similarity.** Parse each supplied area into its geographic level (country, state/province/region, county/metro, city/locality), then map each value to the corresponding documented field and preserve all explicitly requested levels. Do not put a country in an admin-level field, place a city in a generic `place` field when the endpoint expects that city's administrative level, or shift a region into a country/state-code field. Use a canonical country code only when the field or documentation expects one; keep subarea names in their matching fields.
- **Validate the final response.** Follow the required response format exactly, including tool names, call-object keys, and any requested call ordering. Return one list object per call, with that call's required and optional parameter arrays nested inside the object—not at the list level or shared across calls. Serialize each parameter as `{ "name": ..., "value": ... }`, and include empty arrays when a group has no parameters. Cross-check every parameter against the tool schema: place required parameters only in the required array and optional parameters only in the optional array, even when the user explicitly requests an optional field. Check that every requested operation is covered, no unrelated call was added, and the JSON parses. When the format requires only JSON, return no surrounding commentary.

Treat each explicitly described action as a deliverable, including searches mentioned in a multi-step narrative; do not omit a search merely because the prompt also names a specific item found afterward. Distinguish the requested result from its topic: for example, use Moka News: By Source (New) with source=cnn for current CNN news, not CNN Arabic; use Coronavirus Smartable: GetStats for requested COVID statistics, not GetNews, and make a separate call for each country; use dev-to-api: Get all the latest articles for latest posts, not Get all the relevant articles. For a generic request to search travel locations, use the broad location operation and its documented all-scope selector (for example, Priceline com Provider: Search hotels locations with search_type=ALL), not an arbitrary cars-location search. Respect optionality shown in the schema: airportInfo’s iata is optional, and a requested filter does not become required just because it is important. Do not add an unrequested politician limit; when asked for active federal politicians, pass active=true and the canonical optional level_of_government value Federal.

When a user asks for comprehensive checks on both an address and its domain, identify each requested check separately and cover each with the documented operation that performs it. Do not treat one broad email validator as a substitute for an explicitly requested domain-disposable or domain-legitimacy check; conversely, do not add checks the user did not request. Keep each address or domain attached to the appropriate call. For hotel details, include the documented review offset when reviews are explicitly requested (for example, offset_of_reviews=0), and ensure the endpoint covers any other explicitly requested facet such as images.

Translate user-facing names only into the exact representation the endpoint expects: use domain=de for Amazon Germany when that API expects the marketplace code, and use publisher hostnames rather than display names when the news schema expects domains. Carry explicit market settings into every relevant call when supported; for example, use the documented US and en-US selectors on the relevant ASOS requests. For an AliExpress base-region lookup, use the documented User Basic Parameters operation with filter=baseRegion, not an item-search request that merely happens to accept a region.

Apply requested modes and bounds rather than relying on defaults: “first 20” means page=1 and pageSize=20; a free PC game giveaway request should include the documented game type, PC platform, and requested date sort; a standard-deck card draw should use the documented all-suits and all-values settings and disable the card back when those selectors are available. Preserve canonical enum spelling and casing from the tool documentation, keep optional parameters in the optional group, and never invent a limit or other default to make a call seem more complete.
