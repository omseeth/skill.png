# Tool Calling Skill

## Learned rules

- **Implement specified behavior for execution requests.** When the user asks to run, test, or compile a program and describes its intended behavior or algorithm without providing source code, call the appropriate execution endpoint and write minimal executable code that implements that description. Use supplied data and only necessary standard or reasonably inferable constants; do not omit the call solely because the source text is absent. Do not fabricate essential inputs that cannot reasonably be inferred.

- **Map each requested deliverable to the endpoint that performs it.** Break a multi-part query into distinct requested outputs or facets, recording each subject and its constraints before choosing endpoints; keep each clause's values attached to the entity it describes. Choose the most directly fitting documented endpoint using its exact `Provider: endpoint` name. For a single broad deliverable, prefer a documented broad or all-scope endpoint when it fully provides the requested output. For explicitly distinct deliverables, check coverage facet by facet and use a direct endpoint for each requested facet when available, even if another endpoint returns overlapping information; include a general-details endpoint when general details are requested in addition to named facets. For each candidate call, identify the requested clause it fulfills and verify the endpoint source and action match. Use only one best-fitting endpoint for a given subject and facet; prune calls justified only by topical association or a broad goal such as a comprehensive overview, and do not call equivalent validators or searches merely to increase confidence. Keep overlapping-provider alternatives only when they provide distinct requested outputs. For each candidate, verify that its result fulfills the requested action for the right entity and scope: suggestions, checks of weaker properties, or unfiltered results do not substitute for a requested lookup, verification, or scoped result. Keep only calls that cover distinct requested results; reject speculative, duplicate, or adjacent calls, and candidates whose schemas cannot express the requested target without misusing fields or inventing arguments. Do not fan out across generic tools or marketplaces merely because the user did not specify a source. Use a fallback only when it genuinely satisfies the action; do not choose a contradictory endpoint or add unrelated calls merely because they share a topic.
- **Scope and bundle calls appropriately.** Make separate calls for distinct targets, checks, or purposes when they require distinct arguments. Combine multiple filters or categories in one call when they concern the same operation and the endpoint supports that syntax. Do not repeat a check, add overlapping searches, or introduce unrequested calls.

- **Handle independent calls, pagination, and explicit sorting requests.** Issue calls for independent required operations together rather than waiting for one to finish when the tool interface supports it. When the user explicitly requests the first page, pass `page=1` on every applicable paginated call; do the same where applicable when a requested count is served by a paginated endpoint. When the user requests multiple pages or more results from a collection already queried, use distinct sequential page values and retain any requested page size rather than repeating the first page by default. If the user explicitly requests default sorting and the endpoint exposes a documented default-sort value, use that value; do not guess or add unrelated parameters.

Also map named sort intent to the exact documented token (for example, “most relevant” to `RELEVANCE` when that enum is listed). Do not omit a requested sort merely because the sort parameter is optional.
- **Build arguments from the endpoint schema.** Use exact parameter names, satisfy the schema's semantic types, include every required parameter, and put parameters in the required or optional group specified by the tool. Carry every explicit or clearly implied constraint into its matching documented field, including optional qualifiers such as location or area, active status, locale, sort, postal code, duration, quantity, source, or output mode; a broader or unfiltered response is not a substitute when the endpoint supports the requested scope. Include optional fields only when requested or clearly implied, not as speculative defaults. Map a requested count to the documented count field or `per_page`/`limit`; when the user asks for one result and the endpoint has a count field, set it to 1. If no count is requested, use the smallest conventional value needed. Preserve query values and their entity associations, converting them only to documented formats such as API codes, list syntax, or canonical enum spelling. Match the representation expected by each field: use a canonical slug when the schema requires one and convert quantities to documented units (for example, 5 minutes to 300 seconds). Serialize values according to the required call-format convention: follow explicit examples that consistently encode values as strings, even for numeric or boolean parameters; otherwise follow the declared schema types. Never invent enum tokens, identifiers, credentials, or empty placeholders. When a request specifies a market or locale, populate directly corresponding documented parameters (such as country, store, currency, or language) when their values are documented or unambiguously implied; use canonical codes and a market-specific locale when a documented mapping establishes one. For multiple markets, make a separate call per market and keep each market's settings together. Include related regional settings only when the request and documented mapping support them; do not invent opaque identifiers or guess unavailable mappings. Infer locale-specific units or currency only when the user's geography, including an explicitly requested market, unambiguously implies one and the schema documents the exact value; otherwise omit them rather than guess. Distinguish fields for different levels of a location hierarchy.

Before finalizing, scan optional schema fields for controls needed to express the requested output scope, such as inclusion flags and filters. Set applicable controls and leave unrelated optional fields unset.
- **Validate the final response.** Follow the required response format exactly, including tool names, call-object keys, and any requested call ordering. Return one list object per call, with that call's required and optional parameter arrays nested inside the object—not at the list level or shared across calls. Serialize each parameter as `{ "name": ..., "value": ... }`, and include empty arrays when a group has no parameters. Check that every requested operation is covered, no unrelated call was added, and the JSON parses. When the format requires only JSON, return no surrounding commentary.
