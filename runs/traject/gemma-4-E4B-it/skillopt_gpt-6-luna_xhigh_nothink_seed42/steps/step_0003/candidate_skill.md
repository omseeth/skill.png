# Tool Calling Skill

## Learned rules

- **Map each requested deliverable to the endpoint that performs it.** Break a multi-part query into distinct requested outputs or facets, recording each subject and its constraints before choosing endpoints; keep each clause's values attached to the entity it describes. Choose the most directly fitting documented endpoint using its exact `Provider: endpoint` name. For a broad request, prefer a documented broad or all-scope endpoint when it fully provides the requested output; do not choose a narrower endpoint merely because it has fewer required arguments. Conversely, cover separately requested outputs when they require distinct endpoints rather than assuming one broad or multi-capability lookup covers every facet. For each candidate, verify that its result fulfills the requested action for the right entity and scope: suggestions, checks of weaker properties, or unfiltered results do not substitute for a requested lookup, verification, or scoped result. Keep only calls that cover distinct requested results; reject speculative, duplicate, or adjacent calls, and candidates whose schemas cannot express the requested target without misusing fields or inventing arguments. Do not fan out across generic tools or marketplaces merely because the user did not specify a source. Use a fallback only when it genuinely satisfies the action; do not choose a contradictory endpoint or add unrelated calls merely because they share a topic.
- **Scope and bundle calls appropriately.** Make separate calls for distinct targets, checks, or purposes when they require distinct arguments. Combine multiple filters or categories in one call when they concern the same operation and the endpoint supports that syntax. Do not repeat a check, add overlapping searches, or introduce unrequested calls.

- **Handle independent calls, pagination, and explicit sorting requests.** Issue calls for independent required operations together rather than waiting for one to finish when the tool interface supports it. Treat a request to retrieve a collection or perform a search as an initial-page request when no page is specified: pass the documented first-page value (usually `1`) to applicable paginated endpoints, even if the user did not explicitly say “first page.” When the user explicitly requests the first page, pass `page=1` on every applicable paginated call; do the same where applicable when a requested count is served by a paginated endpoint. For initial list or search calls, use a documented default-sort value when the endpoint convention calls for it; do not guess. When the user requests multiple pages or more results from a collection already queried, use distinct sequential page values and retain any requested page size rather than repeating the first page by default. If the user explicitly requests default sorting and the endpoint exposes a documented default-sort value, use that value; do not guess or add unrelated parameters.
- **Build arguments from the endpoint schema.** Use exact parameter names, satisfy the schema's semantic types, include every required parameter, and put parameters in the required or optional group specified by the tool. Carry every explicit or clearly implied constraint into its matching documented field, including optional qualifiers such as location or area, active status, locale, sort, postal code, duration, quantity, source, or output mode; a broader or unfiltered response is not a substitute when the endpoint supports the requested scope. Include optional fields only when requested or clearly implied, not as speculative defaults. Map a requested count to the documented count field or `per_page`/`limit`; when the user asks for one result and the endpoint has a count field, set it to 1. If no count is requested, use the smallest conventional value needed. Preserve query values and their entity associations, but distinguish the user's display-form wording from the endpoint's expected value. Check parameter descriptions and examples for required forms such as a slug, market code, hostname, or enum casing; convert only when endpoint documentation or an unambiguous standard mapping establishes the exact form. For a parameter that selects an operation or mode, use the documented value corresponding to the requested operation. Do not alter wording or casing just for style, substitute a different valid-looking token, or invent an undocumented encoding or opaque value. Match the representation expected by each field: use a canonical slug when the schema requires one and convert quantities to documented units (for example, 5 minutes to 300 seconds). Serialize values according to the required call-format convention: follow explicit examples that consistently encode values as strings, even for numeric or boolean parameters; otherwise follow the declared schema types. Never invent enum tokens, identifiers, credentials, or empty placeholders. When a request specifies a market or locale, populate directly corresponding documented parameters (such as country, store, currency, or language) when their values are documented or unambiguously implied; use canonical codes and a market-specific locale when a documented mapping establishes one. For multiple markets, make a separate call per market and keep each market's settings together. Include related regional settings only when the request and documented mapping support them; do not invent opaque identifiers or guess unavailable mappings. Infer locale-specific units or currency only when the user's geography, including an explicitly requested market, unambiguously implies one and the schema documents the exact value; otherwise omit them rather than guess. Distinguish fields for different levels of a location hierarchy.

- **Honor documented request-format headers.** When an endpoint schema exposes a `Content-Type` parameter and its request format implies JSON, set it to `application/json` even if the user did not explicitly request a format. Treat this as transport metadata, not an unrequested content filter.
- **Validate the final response.** Follow the required response format exactly, including tool names, call-object keys, and any requested call ordering. Return one list object per call, with that call's required and optional parameter arrays nested inside the object—not at the list level or shared across calls. Serialize each parameter as `{ "name": ..., "value": ... }`, and include empty arrays when a group has no parameters. Check that every requested operation is covered, no unrelated call was added, and the JSON parses. When the format requires only JSON, return no surrounding commentary.

## Additional preflight checks

- **Use the supplied tool inventory as a closed set.** Never infer or emit an endpoint name absent from the available tools. Compare candidates using the endpoint-specific operation and schema, not just a provider's broad description. If a requested source has no dedicated endpoint, use a listed source-selectable endpoint only when its documented parameters can express that source and a source identifier is documented or unambiguous; otherwise do not substitute an adjacent feed.
- **Represent explicitly unrestricted scope.** When a request clearly calls for all categories, an unrestricted selection, or a standard full set, provide documented or unambiguous `all`/default values for exposed scope controls when omitting them could narrow or change the result. Apply documented format or protocol settings when the endpoint contract calls for them. Do not guess unsupported enum values or defaults.
