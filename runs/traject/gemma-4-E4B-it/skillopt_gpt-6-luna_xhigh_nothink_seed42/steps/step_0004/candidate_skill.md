# Tool Calling Skill

## Learned rules

- **Map each requested deliverable to the endpoint that performs it.** Break a multi-part query into distinct requested outputs or facets, recording each subject and its constraints before choosing endpoints; keep each clause's values attached to the entity it describes. Choose the most directly fitting documented endpoint by comparing its operation and parameter schema against the full requested action, entity, and scope. In the call's tool-name field, copy the exact canonical inventory identity using the listed provider and API names (`Provider: API name`); do not use descriptive blurbs, paraphrase or abbreviate the name, or alter its punctuation. For a broad request, prefer a documented broad or all-scope endpoint when it fully provides the requested output; do not choose a narrower endpoint merely because it has fewer required arguments. Conversely, cover separately requested outputs when they require distinct endpoints rather than assuming one broad or multi-capability lookup covers every facet. For each candidate, verify that its result fulfills the requested action for the right entity and scope: suggestions, checks of weaker properties, or unfiltered results do not substitute for a requested lookup, verification, or scoped result. Keep only calls that cover distinct requested results; reject speculative, duplicate, or adjacent calls, and candidates whose schemas cannot express the requested target without misusing fields or inventing arguments. Do not fan out across generic tools or marketplaces merely because the user did not specify a source. Use a fallback only when it genuinely satisfies the action; do not choose a contradictory endpoint or add unrelated calls merely because they share a topic.
- **Scope and bundle calls appropriately.** Make separate calls for distinct targets, checks, or purposes when they require distinct arguments. Combine multiple filters or categories in one call when they concern the same operation and the endpoint supports that syntax. Do not repeat a check, add overlapping searches, or introduce unrequested calls.

- **Handle independent calls, pagination, and explicit sorting requests.** Issue calls for independent required operations together rather than waiting for one to finish when the tool interface supports it. When the user explicitly requests the first page, pass `page=1` on every applicable paginated call; do the same where applicable when a requested count is served by a paginated endpoint. When the user requests multiple pages or more results from a collection already queried, use distinct sequential page values and retain any requested page size rather than repeating the first page by default. If the user explicitly requests default sorting and the endpoint exposes a documented default-sort value, use that value; do not guess or add unrelated parameters.
- **Build arguments from the endpoint schema.** Use exact parameter names, satisfy the schema's semantic types, include every required parameter, and put parameters in the required or optional group specified by the tool. Carry every explicit or clearly implied constraint into its matching documented field, including optional qualifiers such as location or area, active status, locale, sort, postal code, duration, quantity, source, or output mode; a broader or unfiltered response is not a substitute when the endpoint supports the requested scope. Include optional fields only when requested or clearly implied, not as speculative defaults. Map a requested count to the documented count field or `per_page`/`limit`; when the user asks for one result and the endpoint has a count field, set it to 1. If no count is requested, use the smallest conventional value needed. Preserve query values and their entity associations, converting them only to documented formats such as API codes, list syntax, or canonical enum spelling. Match the representation expected by each field: use a canonical slug when the schema requires one and convert quantities to documented units (for example, 5 minutes to 300 seconds). Serialize values according to the required call-format convention. When examples show numeric parameter values as strings, use that representation even for NUMBER fields; do not coerce values solely from the schema's semantic type. Preserve booleans in the type indicated by the format or examples. Never invent enum tokens, identifiers, credentials, or empty placeholders. When the user explicitly supplies a value that directly matches a documented enum field's meaning, pass that value using its canonical spelling even if the allowed enum values are not listed; omit it only when the mapping is ambiguous. When a request specifies a market or locale, populate directly corresponding documented parameters (such as country, store, currency, or language) when their values are documented or unambiguously implied; use canonical codes and a market-specific locale when a documented mapping establishes one. For multiple markets, make a separate call per market and keep each market's settings together. Include related regional settings only when the request and documented mapping support them; do not invent opaque identifiers or guess unavailable mappings. Infer locale-specific units or currency only when the user's geography, including an explicitly requested market, unambiguously implies one and the schema documents the exact value; otherwise omit them rather than guess. Map locations from country outward using the user's parent-to-child geography and the endpoint's documented field semantics. Country, region/state, city, and postal code are distinct levels; a field named `state` may represent a different level in a particular schema. Keep representations distinct as well: country codes, marketplace domains or hostnames, locales, and API-specific or country-ID tokens are not interchangeable. Bind each value only to a field matching its level and type, follow documented allowed values and casing, and use a documented or unambiguous mapping (or a listed lookup endpoint) for opaque identifiers. Do not guess, shift nested places, or repurpose fields. Carry an unambiguous geographic or market clue to related calls only through matching documented regional fields, and do not transfer settings to a clearly separate market.
- **Validate the final response.** Follow the required response format exactly, including tool names, call-object keys, and any requested call ordering. Return one list object per call, with that call's required and optional parameter arrays nested inside the object—not at the list level or shared across calls. Serialize each parameter as `{ "name": ..., "value": ... }`, and include empty arrays when a group has no parameters. Check that every requested operation is covered, no unrelated call was added, and the JSON parses. When the format requires only JSON, return no surrounding commentary.
