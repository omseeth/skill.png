# Tool Calling Skill

## Plan tool calls

- Before choosing tools, maintain a one-row-per-action ledger recording each requested operation, subject and source, constraints, and candidate endpoint. Match each operation independently: a later detail lookup does not fulfill an earlier search, and a past-tense action is not evidence that it has already been executed. For nested scopes, populate all corresponding hierarchy fields in one call when the endpoint schema supports them rather than making overlapping calls for alternative scopes.
- Match an endpoint's full output semantics, not just its topic: for a compound result, prefer an endpoint documented to provide all requested properties. Match the requested time horizon and map it to a supported duration field; a current or shorter-horizon endpoint is not equivalent to a multi-day forecast.
- For explicit find, search, list, or browse requests, use a documented search or list operation when available. If none is listed and the same provider's only discovery operation is autocomplete or suggestions, use it for discovery rather than substituting item details or omitting the outcome; make separate calls for separately requested details.
- When the user names multiple providers, treat those names as the requested source scope; broad wording does not authorize additional unnamed sources. For articles published by a named news outlet, prefer its documented source-specific feed and source identifier: a generic keyword search may return articles that merely mention the outlet, and an all-source feed is not an additional outcome unless requested.

- Check temporal scope explicitly: current conditions are not forecasts, and location-specific active alerts are not aggregate alert counts. When coordinates are supplied and a matching coordinate-based endpoint exists, use it rather than inferring a city or changing the location form.
- Turn the query into a checklist of distinct requested outcomes, including each subject, action, and explicit constraint. Keep modifiers attached to the result they qualify. Match each outcome to an endpoint that returns the requested kind and granularity of result, using its actual operation and schema rather than topical similarity (for example, distinguish item-level results from aggregate counts, and suggestions from pricing). Prefer an explicitly named endpoint when available. When the user names a platform or provider, treat it as a source constraint: use a matching endpoint from that source when it fulfills the request, rather than substituting another provider's generic endpoint. Treat each explicit action clause as a requested outcome even when recounted in past tense or embedded in a sequence; do not assume it has already been executed. Narrative transitions alone do not authorize additional calls: include operations named in action clauses, but do not infer operations from contextual goals or comparisons.
- Build the smallest complete call set: cover every requested outcome, and make every call serve one of them. Use one endpoint for multiple outcomes only when it genuinely covers them; make separate calls for distinct inputs unless the schema supports batching. If a requested endpoint is unavailable, use a listed alternative only if it genuinely fulfills the request. Do not invent tools, add unrelated calls, or include redundant alternatives or validators.

- When calls are independent, issue them together rather than treating narrative order as a dependency.

## Ground arguments in the request and schema

- Treat example calls and answer-format samples as syntax demonstrations only. Do not copy sample tool names, parameter names, or values into a task call unless the actual tool schema and user request independently support them.
- For hierarchical location schemas, map a named place to the matching documented level and supply required ancestors using canonical API codes or names. Do not repeat a country as an administrative region or put a city in a parent-level field. Use a separate administrative-division lookup only when needed to resolve canonical values and with all required inputs; do not add an unpopulated lookup call alongside the actual count or search.
- Preserve requested search text, identifiers, and constraints; normalize only as the endpoint requires, without dropping meaningful words or substituting one value or geographic level for another. Map explicit filters, counts, pages, sorting, locale, category, and location to the corresponding schema fields, using accepted representations for enums and locales.

- For a search or list request about a specifically named item, use a documented exact-match control when available to avoid similar-name results, unless the user asks for broad or fuzzy discovery.

- Translate stated market constraints into API-native values according to the tool schema. Keep each constraint scoped to its requested outcome and carry every compatible constraint into the call. Interpret comparison language before selecting fields: longer than, more than, or at least maps to a minimum/lower bound; shorter than, less than, or at most maps to a maximum/upper bound; and a range such as between X and Y uses both bounds when available. Convert units to the endpoint's units. Preserve strictness where supported; otherwise use only the documented closest bound. Never reverse a comparison or collapse a range to a single endpoint. For exact quantities, use an exact-value field or matching lower and upper bounds when supported. Map an exact requested result count, including one, to a supported count, limit, or page-size field; for paginated requests, map both the requested page and result count/page size when available. Select the date field corresponding to the event named in the request, and map semantic filters and sorting to documented API flags or enum values. Use the endpoint's accepted locale form and canonical enum, code, or slug; do not guess undocumented values or substitute a semantically different field when the requested distinction is unavailable. When a user requests a country or region for a localized endpoint, treat it as a regional setting that may determine multiple directly applicable fields exposed by that endpoint, such as country, store, currency, language, or size system. Populate those fields using documented mappings; do not assume one field alone represents the whole setting or fill unrelated fields.
- For each selected endpoint, take parameter names, declared types, and the required-versus-optional partition from that endpoint's own schema; do not borrow fields or bucket assignments from a similar endpoint. Put every required field in the required bucket and every non-required field in the optional bucket, even when the user explicitly requests an optional setting; never duplicate a field or place it in both buckets. Represent values using the declared types in the call object (for example, JSON numbers as numbers and booleans as booleans). If the active answer format explicitly requires a different serialization, such as string-valued name/value entries, follow that wrapper while preserving the value's meaning (for example, use a canonical decimal string). Use accepted enum or API-native forms, including canonical codes, symbols, and casing, while preserving identifiers and free-text search wording. Include optional settings when requested or clearly implied by the requested result: map semantic qualifiers to documented endpoint filters, and interpret scope phrases such as “main page” using the endpoint's documented identifier. For open-ended list/feed or recent-history requests, use the first page and a modest supported page size or limit when pagination controls exist and no page or count was specified; do not add these to fixed-size endpoints or invent undocumented values. Use documented recency or freshness controls for requests such as “recent” or “latest.” Do not invent dates, defaults, limits, IDs, credentials, filler values, or other unsupported constraints. If a required value is missing, do not fabricate it.

## Validate before responding

- If the active answer format specifies an order for calls (for example, sorting by tool name), reorder the completed call objects to match it before responding; do not retain narrative task order.
- Before responding, perform a two-way audit: map every requested outcome to the call or calls that fulfill it, checking each endpoint's operation, source, and requested result granularity; then ensure every call serves at least one requested outcome and remove unmatched calls. For each remaining call, compare its arguments field by field with that endpoint's schema and the request: use exact parameter names and declared types, place each parameter exactly once in the required or optional bucket specified by the schema, and include each compatible explicit constraint in its accepted form. When supported, preserve both bounds of a range rather than using an exact-value field. Omit unsupported or unrequested values, and do not fabricate missing required values. Emit one call object per endpoint invocation. Finally, validate the complete response as valid JSON in the exact active format and wrapper, with exact tool names, allowed keys, required empty arrays, and well-formed parameter objects; check for duplicate keys, malformed wrappers, bundled calls, or extra text.
