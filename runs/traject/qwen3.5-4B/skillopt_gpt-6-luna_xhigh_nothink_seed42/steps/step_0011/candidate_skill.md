# Tool Calling Skill

## Plan tool calls

- Treat endpoint eligibility as a gate: confirm the endpoint's own operation and schema support the requested result kind and granularity, and can represent every compatible explicit qualifier. A topical neighbor or broader operation is not sufficient. A named provider or source is a hard constraint for that outcome; do not fulfill or supplement it with another provider when a fitting named-source endpoint exists.

- Match the requested entity level and property as well as the topic: a result about a related component or sub-entity does not fulfill a request about the main entity, even when the search terms overlap.
- Deduplicate identical calls unless the user explicitly requests separate or repeated passes. Preserve separate invocations for separately requested passes—even when the endpoint and entity recur, such as an explicit repeat, a second sort, or a request for more items. For a “more” or “next page” request, use the next page or index only when the schema supports pagination and the wording establishes continuation; retain each pass’s requested filters or sorting. Do not infer repetition or pagination from narrative context alone. Do not add related calls as extra checks. An explicitly requested draw or simulation is its own outcome and requires the corresponding draw or simulation operation, not a related catalog or list endpoint.
- When several requested checks concern the same subject, first look for a single endpoint whose documented operation explicitly returns all the requested properties, and prefer it over multiple narrower calls when it fully covers the outcomes. Do not infer endpoint functionality from a provider-wide description or add a secondary validator whose result is already covered; split the checks only when no endpoint genuinely covers them together.

- Check temporal scope explicitly: current conditions are not forecasts, and location-specific active alerts are not aggregate alert counts. When coordinates are supplied and a matching coordinate-based endpoint exists, use it rather than inferring a city or changing the location form.
- Turn the query into a checklist of distinct requested outcomes, including each subject, action, and explicit constraint. Keep modifiers attached to the result they qualify: a location, source, country, category, date, or unit in one clause does not automatically constrain a neighboring outcome unless the wording clearly scopes it across both. For each outcome, require a candidate endpoint to satisfy all compatible explicit constraints; do not add a partially matching call as a supplement when an endpoint covers the fully constrained outcome. Match each outcome to an endpoint that returns the requested kind and granularity of result, using its actual operation and schema rather than topical similarity (for example, distinguish item-level results from aggregate counts, and suggestions from pricing). Prefer an explicitly named endpoint when available. When the user names a platform or provider, treat it as a source constraint: use a matching endpoint from that source when it fulfills the request, rather than substituting another provider's generic endpoint. Treat each explicit action clause as a requested outcome even when recounted in past tense or embedded in a sequence; do not assume it has already been executed. Narrative transitions alone do not authorize additional calls: include operations named in action clauses, but do not infer operations from contextual goals or comparisons.
- Build the smallest complete call set: cover every requested outcome, and make every call serve one of them. Use one endpoint for multiple outcomes only when it genuinely covers them; make separate calls for distinct inputs unless the schema supports batching. If a requested endpoint is unavailable, use a listed alternative only if it genuinely fulfills the request. Do not invent tools, add unrelated calls, or include redundant alternatives or validators.

- When calls are independent, issue them together rather than treating narrative order as a dependency.

## Ground arguments in the request and schema

- For every numeric constraint, compare the user's unit with the selected field's documented unit and convert before setting the value, regardless of domain (for example, minutes to seconds). Preserve the comparison direction and convert both bounds. Never copy a number unchanged across mismatched units, and do not guess when the schema provides no conversion basis.
- In formats that represent parameters as name/value entries, serialize each schema parameter as its own `{ "name": "<exact field>", "value": <concrete value> }` entry. Do not pack multiple parameters into a single object keyed by parameter names.
- Preserve requested search text, identifiers, and constraints; normalize only as the endpoint requires, without dropping meaningful words or substituting one value or geographic level for another. Map explicit filters, counts, pages, sorting, locale, category, and location to the corresponding schema fields, using accepted representations for enums and locales.

- For optional search-mode, entity-type, platform, category, or format selectors, use the documented choice matching a class, mode, platform, or format clearly identified by the requested result—even when expressed as a descriptor rather than as “filter by” (for example, “PC game giveaways”). Do not choose an arbitrary restrictive value for another selector dimension the user left unspecified; omit it, or use a documented all/any value only when needed to express the requested scope.
- If a schema declares an enum but does not list its accepted values, do not replace a user-stated label with a synonym or guessed canonical spelling; retain the literal term when its meaning is clear, and do not guess when support is unclear. Preserve the spelling and case of named source values unless the endpoint documents normalization.

- Map every numeric range or threshold to the endpoint's corresponding filter fields, regardless of domain. When both bounds are available, set both; keep range bounds distinct from result counts and page sizes. For example, a requested length range maps to minimum- and maximum-length fields, not a per-page count. Do not omit a bound or repurpose a count field.

- For a search or list request about a specifically named item, use a documented exact-match control when available to avoid similar-name results, unless the user asks for broad or fuzzy discovery.

- Translate stated market constraints into API-native values according to the tool schema. Keep each constraint scoped to its requested outcome and carry every compatible constraint into the call. Preserve both bounds of a stated range when corresponding minimum and maximum fields are available; preserve comparison direction and units (for example, map “at least” to a minimum and “at most” to a maximum, converting to the schema's units). For exact quantities, use an exact-value field or matching lower and upper bounds when supported. Map an exact requested result count, including one, to a supported count, limit, or page-size field; for paginated requests, map both the requested page and result count/page size when available. Select the date field corresponding to the event named in the request, and map semantic filters and sorting to documented API flags or enum values. Use the endpoint's accepted locale form and canonical enum, code, or slug; do not guess undocumented values or substitute a semantically different field when the requested distinction is unavailable.
- For each selected endpoint, use only its own schema for exact parameter names, declared types, and required/optional placement; never borrow fields from similar operations. For parameters you include, put every required field in the required bucket and every non-required field in the optional bucket, even when the user explicitly requests an optional setting; never duplicate a field. In formats that represent parameters as name/value entries, every entry must contain the exact name and a concrete non-null value—never emit name-only entries or null placeholders. Bind required values to the request or a documented derivation; if a required value is missing, do not call that endpoint rather than fabricate it. Treat documented finite choices as API-native values even if typed STRING, and use documented canonical codes and casing; preserve identifiers and free-text wording except where the endpoint specifies normalization. Include optional settings only when requested or clearly implied; use documented freshness controls for “recent” or “latest” and a modest supported result count for “some” or an open-ended list request (such as top headlines), when a count or limit field is available and the endpoint is not fixed-size. Do not invent dates, defaults, limits, IDs, credentials, filler values, or other unsupported constraints.

- Distinguish exhaustive requests (“all,” “complete,” or a naturally finite set such as all states) from requests for “some”: when the endpoint documents an all/full-results control or limit/pagination setting, use it to cover the requested collection rather than applying a modest sample size. Do not invent caps or pagination beyond documented controls.

## Validate before responding

- For a list-of-calls response, each array element must be one complete invocation with one tool name; repeated invocations, including repeated calls to the same endpoint, remain separate elements. Never put multiple tool names in one object or repeat wrapper or parameter keys to encode more calls. Check that every intended invocation has its own element and that parsing the final JSON would retain every element and field.

- If the active answer format specifies an order for calls (for example, sorting by tool name), reorder the completed call objects to match it before responding; do not retain narrative task order.
- Before responding, run a concise call-by-call, two-way audit: map every requested outcome to a fitting call and remove any call that serves none. Verify each call's operation, source, requested entity/property, and result granularity, and copy the exact tool identifier from the tool list. Check every argument against that endpoint's own schema and the request: exact field, grounded value with the documented type and canonical form, required-versus-optional placement exactly once, and every compatible explicit constraint. Encode values using the active format's required wire representation. Preserve supported counts, pages, and range bounds; omit unsupported or unrequested values, and never fabricate missing required inputs or use blank/null placeholders. In name/value-entry formats, emit one entry per parameter, never a packed object. Emit one invocation per object, then verify the complete response parses as valid JSON in the exact required wrapper and keys, including required empty arrays.
