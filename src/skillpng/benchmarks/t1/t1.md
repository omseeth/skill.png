## 1. What the task is

T1 (Chakraborty et al., NeurIPS 2025 Datasets & Benchmarks,
[CapitalOne-Research/T1](https://github.com/CapitalOne-Research/T1)) is a dataset of multi-turn
travel-planning conversations between a user and an assistant, covering flights, hotels,
restaurants and attractions. Every user turn comes with a **plan**: a few lines of Python that do
what the assistant has to do at that point. A plan can

- **call tools** that query T1's travel database: search tools (`search_flights`,
  `search_hotels`, …), filter tools that narrow earlier results (`filter_hotels`, …), and the
  helpers `search_nearest`, `sort_results` and `adjust_date`;
- **ask for missing details** with `seek_information("…")`, when something the search needs, such
  as a date, has not been given yet;
- **keep results for later turns** with `save_to_cache(key, value)`, and read them back with
  `get_results_from_cache(key)`.

Each result set carries a one-line **summary** of its query and the number of matches. The model
never sees the results themselves, only the **cache summary**, a dict from each cache key to its
summary. The same cache summary, taken after the code has run, is what the headline score compares.

The model's job at an item is to write the plan for one user turn. Its code is executed, and the
turn is scored with T1's metrics.

**An example.** The first three user turns of dialogue 23 in
`flighthotel/test/output_file_flighthotel_test_17.csv`, with their gold plans:

```
assistant: Hello, how can I assist your travel plans?
user:      I'm looking for a flight from Santa Ana to Tampa and a hotel in Tampa for a weekend
           getaway
  plan:    seek_information("We need to ask for the departure date for flight, check in date
                             and check out date for hotel.")
assistant: What are your travel dates and preferred class of service?
user:      We're traveling on May 15, 2025 and prefer first
  plan:    flights = search_flights(start_airport_city="Santa Ana", end_airport_city="Tampa",
                                    departure_date=["May 15, 2025"], flight_class=["first"])
           save_to_cache(key="flights", value=flights)
assistant: And for the hotel, what kind of accommodations are you looking for?
user:      A 4 star hotel in Downtown Tampa for 4 nights with a gym and rooftop bar
  plan:    checkout_date = adjust_date(date="May 15, 2025", delta_days=4)
           hotels = search_hotels(city="Tampa", checkin_date=["May 15, 2025"],
                                  checkout_date=[checkout_date], stars=[4, 4],
                                  neighborhood=["Downtown Tampa"], gym_present=True,
                                  has_rooftop_bar=True)
           save_to_cache(key="hotels", value=hotels)
```

At the third user turn the model sees the conversation up to "…with a gym and rooftop bar" and
the cache summary

```
{'flights': 'Flight search results from Santa Ana to Tampa, departing on date(s) [2025-05-15].
             flight classes: [first], max number of layover(s): 1, max layover 1 duration:
             60 minutes.\nThere are 2 flight(s) that matched this query!'}
```

After the gold plan, the cache also holds `'Hotel search results in Tampa from check-in date(s)
[2025-05-15] to check-out date(s) [2025-05-19]. stars range: [4, 4], neighborhood(s): [Downtown
Tampa], gym_present, has_rooftop_bar.\nThere are 3 hotel(s) that matched this query!'`. The model
gets full marks if its code leaves the cache with the same summaries, whatever new key it saves
the hotels under. Forgetting `gym_present=True`, miscounting the nights or not saving the result
scores 0.

**An item is one user turn, scored teacher-forced.** The model always sees the correct
conversation so far and the correct cache summary, never its own earlier answers, and its code
runs on the state the gold plans have built up to that turn. So every item is one prompt and one
answer, and a mistake at one turn never affects another.

```
system: You are an expert AI travel planner and your responsibility is to generate Python code
        using APIs or Tools.                                       # benchmark.system_prompt
user:   Your task is to generate a Python code based on a conversation ...
        # TOOL CONFIG        15 tools, 46,568 characters, 11,860 tokens
        # INSTRUCTIONS       track state, don't invent values, seek_information, the cache
        # OUTPUT FORMAT      code only, in <CODE> </CODE>; tools are predefined, keyword args
        # CONVERSATION       [{'assistant': ' Hi, ...'}, {'user': ' I need a flight ...'}]
        # CACHE              {'flights': 'Flight search results from ... There are 12 ...'}
        Given the provided conversation and cache summary, generate a Python code for the last
        user turn.                                                 # data/t1_prompt.txt
```

**The prompt is T1's own planning prompt, zero-shot.** It documents all 15 tools (TOOL CONFIG,
most of the prompt's length), states T1's planning rules and the output format, then shows the
conversation and the cache summary. T1's prompt also carries 13 worked examples and asks for
reasoning before the code; here the examples are removed and the output format asks for code only.
What the examples showed by example is stated instead, because zero-shot models otherwise crash
on it: the tools are already defined and are neither imported nor redefined, every tool but
`seek_information` takes keyword arguments only, `find_nearest` is not available (T1 documents
the nearest tool twice, once under that undefined name; both entries say `search_nearest`), earlier
results are read from the cache, and every search, filter, sort and nearest result is saved
with `save_to_cache(key=..., value=...)` (T1's own rule passes the key positionally, which
the keyword-only tool rejects, and saves only what "could be reused").
The conversation and the cache are shown exactly as T1 shows them: the conversation as a Python
list of one-key dicts, the cache as the summary dict before the turn, `{}` when empty.

T1 sends its system text and the prompt as one message. Here the system text is its own turn, so
the `llmskill` and `skillpng_llmskill` conditions add to it as they do on every benchmark.

The template is `data/t1_prompt.txt`, written by `t1_build prompt`. Its sha256 is recorded in the
split manifest and checked at load. The file contains meaningful trailing whitespace: an editor
that strips it changes every prompt, and the adapter then refuses the template.

Runs before 2026-10-01 used an earlier template (sha256 `92a6133e…`) without the conventions
above. Every model scored the do-nothing floor on it (§4), crashing on nearly every tools item;
those scores are not comparable with later ones.

The image goes into the user turn at `injection.site`: `pre_query` before "Your task is…", ahead
of the TOOL CONFIG; `post_query` after "…for the last user turn.".

**Target** (what the training loss is taken on): the gold plan in `<CODE>` tags,
`"<CODE>\n" + Filled_Plan.strip() + "\n</CODE>"`.

**Answer** (what is executed): everything up to the last `</think>` is dropped, then the **last**
`<CODE>` block in what remains is stripped and run; a block never spans a second opener, so a
trace that only names the tag ("wrap it in `<CODE>` tags") cannot swallow the real block after it.
An output without a `<CODE>` block counts as empty code. T1's own evaluation joins every block
instead. The two agree on a single block, but Gemma 4's reasoning trace reaches us without a
`</think>` (vLLM strips its channel tokens and leaves a bare `thought` prefix), so joining would
run the trace's draft code before the answer.

## 2. Corpus and split

T1 has **9 domains**: four single ones (flight, hotel, restaurant, attraction) and five
combinations (flighthotel, hotelrestaurant, hotelattraction, flighthotelrestaurant,
flighthotelattraction). Dialogues are written as **templates** with placeholders (`<CITY_1>`,
`<DEPARTURE_DATE_1>`, …), and each template is filled in 25 times with different cities, dates and
preferences, once in each of the 25 files of its domain and split. Per domain there are 15 train,
5 validation and 40 test templates.

At the pinned revision (`7a3e583`, 2025-10-07) that is 675 dialogue CSVs
(`<domain>/<split>/output_file_<domain>_<split>_<n>.csv`, n = 1..25), 13,500 dialogues and
61,150 user turns (train 15,000, validation 5,175, test 40,975). `t1_build audit` asserts every
one of these counts.

**An item id is `{domain}:{hf_split}:{file_index}:{ID}:{turn}`**, where `ID` is the template and
`turn` counts the dialogue's user turns from 0. `flighthotel:test:17:23:2` is the third user turn of
template 23 in `flighthotel/test/output_file_flighthotel_test_17.csv`, the turn in the example
above (not itself a shipped item).

### Eligibility

T1 runs the gold plans of a whole file in one shared Python namespace, so variables defined in one
dialogue stay visible in the dialogues after it. Some gold plans rely on this by accident: they
read a variable, such as `hotels`, that their own dialogue never defined, and only run because an
earlier dialogue of the file left one behind. They then work on that other dialogue's results.

This adapter replays each dialogue in a namespace of its own (**session replay**), where those
plans fail. A user turn is used only when:

1. it has a gold plan;
2. under session replay, no gold plan of its dialogue up to and including this turn raises an
   error;
3. session replay and T1's file-wide replay agree on every turn of the dialogue up to and
   including this one: the same cache summary before and after, and the same errors.

| rule | train | validation | test |
|---|---|---|---|
| user turns | 15,000 | 5,175 | 40,975 |
| 1. no gold plan | −725 | −175 | −1,375 |
| 2. a gold plan raises | −118 | 0 | −500 |
| 3. leak-dependent | 0 | 0 | 0 |
| **eligible** | **14,157** | **5,000** | **39,100** |

Rule 3 removes nothing beyond rule 2, because every turn affected by the leak already fails rule 2.
It is kept because it guarantees that **on every shipped item our gold is the paper's gold**.
Test template 26 of flighthotelrestaurant has no eligible turn at all: its second user turn calls
`search_nearest(hotels=hotels, …)` before `hotels` exists, which only runs in T1 because a variable
of the same name leaks in from another dialogue of the file.

### Selection

400 train / 200 val / 1,400 test items, drawn from T1's train, validation and test splits
respectively. T1's splits share no templates and no cities, and nothing crosses them here.

The draw is deterministic: every choice ranks candidates by a seeded hash (seed 42), so the split
follows from the rules alone.

1. **Domains:** each domain gets an equal share of the split; the remainder goes to domains chosen
   by hash.
2. **Templates:** within a domain, the share is spread evenly over the templates that have at least
   one eligible turn; the remainder goes to templates chosen by hash.
3. **Turns:** within a template, eligible turns are taken in hash order, at most one per dialogue.
   Every item therefore comes from a different dialogue.

The exact hash keys are in `t1_build.py` and recorded in the manifest.

| domain | train | val | test |
|---|---|---|---|
| flight | 44 | 22 | 156 |
| hotel | 45 | 23 | 156 |
| restaurant | 45 | 22 | 156 |
| attraction | 45 | 22 | 156 |
| flighthotel | 44 | 22 | 156 |
| hotelrestaurant | 44 | 22 | 155 |
| hotelattraction | 45 | 22 | 155 |
| flighthotelrestaurant | 44 | 22 | 155 |
| flighthotelattraction | 44 | 23 | 155 |
| **total** | **400** | **200** | **1,400** |
| **digest** | `36801cec4695bd2b` | `95837288aa261ea2` | `5a35dbd6e99156bf` |

The digest, `sha256("\n".join(sorted(ids)))[:16]`, identifies the split. `items.json` lists each
split in a hash-shuffled order, so any prefix (`benchmark.limit`, `eval.limit`,
`train.eval_items`) still mixes domains.

**`gold_kind`** labels each item by what its gold plan does. It matters for reading scores, because
the headline treats these kinds very differently (§4):

| gold_kind | the gold plan | train | val | test |
|---|---|---|---|---|
| `tools` | calls a search, filter or helper tool, and asks nothing | 283 | 152 | 989 |
| `seek_only` | only asks for missing details with `seek_information` | 85 | 38 | 289 |
| `seek_plus_tools` | both | 18 | 4 | 66 |
| `cache_read_only` | only reads the cache, or calls nothing | 14 | 6 | 56 |

### Files

`data/t1_id_split/split_manifest.json` records the dataset revision, the vendored commit, the seed,
the selection rules, the dropped template, the per-domain counts and digests, the gold kinds, the
prompt's sha256 and the replay semantics. Each `<split>/items.json` entry holds the item's `id`,
its parts (`domain`, `hf_split`, `file_index`, `template_id`, `turn`), its `gold_kind`, and
digests of its gold plan and of the cache summary before the turn.

On first use, `items()` downloads only the dialogue CSVs the split needs, rebuilds every item by
replaying its dialogue, re-checks rules 1 and 2 and every field and digest, and refuses to load
on any mismatch.

## 3. Execution

For every item, a worker process:

1. **rebuilds the state before the turn:** starting from an empty cache, it runs the dialogue's
   earlier gold plans in a fresh namespace, and checks that the cache summary matches the one the
   prompt showed (a mismatch is reported as an error, not scored);
2. **copies that state,** variables and cache together, so a variable and the cache entry it was
   saved to stay one object in the copy;
3. **runs the gold plan** on the original state, which gives the reference cache after the turn;
4. **runs the model's code** on the copy, with the names T1's evaluation provides: every tool,
   the cache functions, `pd`, `os`, `re`, `csv`, `Path` and the `typing` names. `find_nearest` is
   described in T1's TOOL CONFIG (not in this template's) but T1 never defines it, so calling it
   raises a `NameError`, as it does in T1.

Empty code is not run and counts as a success. An error is recorded as its message.
`sys.exit()` and a raised `KeyboardInterrupt` count as the code's error; they do not stop the
worker.

- **Timeout.** The model's code gets `benchmark.options.exec_timeout_s` (30 s); rebuilding the
  state does not count against it. On expiry the worker is killed and a new one starts for the
  next item.
- **I/O.** Stdin is closed, so `input()` fails at once. Printed output is discarded.
- **Isolation.** Every item rebuilds its state from scratch, so nothing carries over between
  items. Any change the code makes to Python builtins or to the tool modules
  (`import builtins; builtins.len = None`) is undone before anything else runs.

**Where this differs from T1.** T1's own scoring runs the model's code for all turns of a file in
sequence, in one namespace, so a variable the model defined at one turn is still there at later
turns. Here every turn starts from the gold state. For correct code both give the same result;
they can differ when a model defines a variable wrongly at one turn and reads it at a later one.
The end-to-end parity test in `tests/test_t1_protocol.py` names every such turn (§7).

## 4. Metrics

Every scored turn produces the numbers below. They are stored in `Result.meta`, so in each row of
`<run>/eval/<split>-<condition>.jsonl`, and computed as T1's evaluation computes them per turn
(`evaluation/generate_evaluation_metrics.py`, on top of the vendored `eval_metrics.py`).

- **`cache_em` (the headline): did the code leave the cache in the right state?** 1 when the cache
  summaries after the model's code are the same as after the gold plan, compared as a multiset of
  summary strings; also 1 when both caches are empty. Key names do not matter, but every saved
  result must come from the same query with the same parameters, and nothing extra may be saved or
  overwritten. Code that timed out or crashed the worker scores 0.
- **Tool calls: `tool_tp/fp/fn` and `tool_f1`.** Calls are read from the code by parsing it, not
  by running it: every call of a plain function name counts, including the cache functions and
  `seek_information`. Gold and generated calls are compared by tool name and count: a tool gold
  calls twice and the model once gives one true positive and one false negative. `tool_f1` is the
  F1 of one turn's counts.
- **Parameters: `param_tp/fp/fn`.** Each gold call is paired with the unused generated call of
  the same tool that shares the most argument values with it, and each equal argument is a true
  positive. The cache functions and `seek_information` are left out, and so are arguments that
  only pass results along (`prior_results`, `hotels`, …) and positional arguments. List values
  are compared regardless of order.
- **`code_success`** is 1 − `non_executable`. `non_executable` is 1 when gold makes calls and the
  model's code either raised an error or made no calls.

Two of T1's rules, kept exactly, change which turns the tool and parameter metrics see:

- A generation whose only call is a single `print` (such as `print("No planning needed")`) has no
  calls. In longer code, `print` calls are dropped.
- Tool and parameter counts are recorded only when the generation has calls in T1's sense. Empty
  code, code that does not parse, or a lone `print` leave the turn out of them entirely. Code
  with no calls at all, or with two `print`s, stays in, with every gold call a false negative.

So a model that answers with a lone `print` is not penalized by T1's precision and recall; the
report therefore prints the share of turns with no calls beside them.

### Which number to report

`score()` returns `benchmark.options.metric`. That is `Result.score`, the number in
`results.jsonl`, and the number `best.png` is selected on under `val_metric`.

| metric | per item | why or why not |
|---|---|---|
| **`cache_em`** (default) | 1 if the cache after the code matches gold | Checks the outcome, not the wording. It is the paper's end-to-end metric, and its mean over items is exactly T1's cache-summary exact match. Binary, so the paired difference between two conditions is simple to read. |
| `tool_f1` | F1 over the turn's tool names | A diagnostic. Its mean is not a number T1 reports: T1 sums the counts over a domain first. |
| `code_success` | 1 if the code ran and made calls where gold does | Too easy for a headline: any call that runs scores 1. |

**`cache_em` has a do-nothing floor.** Code that changes nothing scores 1 wherever the gold plan
also leaves the cache unchanged: every `seek_only` and `cache_read_only` item, plus two `tools`
items. That is **0.2479 on test (347 of 1,400) and 0.2200 on val (44 of 200)**. Always read the
headline against this floor and against the `gold_kind` breakdown.

**The wording of a question is not scored.** On `seek_only` items, `cache_em` only checks that the
model did not search or save anything; a wrong question and a right one score the same. T1's BLEU
score on `seek_information` text is not computed here, and BERTScore, which the paper reports, is
not in T1's evaluation code.

### The report

```bash
python -m skillpng.benchmarks.t1.t1_report runs/t1/<model>/<run>/eval/test-none.jsonl \
  --against runs/t1/<model>/<run>/eval/test-skillpng.jsonl
```

It prints T1's metrics per domain and their macro average over the nine domains (the "Avg." of the
paper's tables), with T1's names and formulas. It does this once over all turns and once over the
turns whose code ran (`exec_only_*`, `non_executable != 1`):

- `tool_calling_micro_*` and `tool_param_micro_*`: precision, recall, F1 and accuracy
  (tp / (tp + fp + fn)), from the counts summed over the domain;
- `code_success_rate`: 1 − the mean `non_executable` per source file, averaged over files;
- `cache_summary_exact_match_avg`: the mean `cache_em` over turns.

Beside them, because T1's numbers alone can mislead on this setup:

- the headline;
- code success as a plain mean over items, because on a sampled split T1's per-file average
  weights files unevenly;
- the share of turns with no tool calls, which T1's precision and recall leave out;
- counts of outputs without a `<CODE>` block, code that did not parse, timeouts and turns not
  executed to an outcome;
- the headline, `cache_em`, code success and the no-call share per `gold_kind`;
- with `--against`, the paired difference between two conditions on the same items, with a
  bootstrap 95% CI and the number of items that got better, worse or stayed the same. The claim
  is a paired difference, not two independent intervals.

**Comparability.** These numbers are **not comparable to the paper's tables**: they cover a
sampled subset of user turns, use the zero-shot prompt (the paper's baselines are few-shot or
fine-tuned), and exclude the leak-dependent turns the paper scores with file-wide gold.

## 5. Token budgets

Measured over the 2,000 items with the `Qwen/Qwen3.5-9B` tokenizer and chat template, thinking
off, system + user + generation prompt; targets without eos or suffix; nearest-rank percentiles:

| tokens | min | p50 | p95 | max |
|---|---|---|---|---|
| prompt | 12,610 | 12,705 | 13,135 | **13,645** |
| target | 7 | 59 | 154 | **277** |
| prompt + target | 12,629 | 12,789 | 13,252 | **13,715** |

Almost all of every prompt is the tool documentation (11,860 tokens); the answers are short. Image
tokens come on top: 64 to 256 depending on the model. base.yaml's `max_sequence_tokens: 10240`
would refuse every item, so `configs/t1.yaml` pins:

```yaml
model:
  max_new_tokens: 4000        # t1's original budget
  max_target_tokens: 512      # max observed 277
  max_sequence_tokens: 16384  # max observed 13,715 + up to 256 image tokens
```

For another tokenizer family, re-measure with
`python -m skillpng.benchmarks.t1.t1_build audit --tokenizer <path>`: a target longer than
`max_target_tokens` is cut silently. For vLLM, `--max-model-len` must cover the longest prompt,
the image and `max_new_tokens`: 20480.

## 6. Running it

```bash
# artifacts, built once, committed, digest-verified on load
python -m skillpng.benchmarks.t1.t1_build prompt
python -m skillpng.benchmarks.t1.t1_build split  --replay-cache /tmp/t1_replays.pkl
python -m skillpng.benchmarks.t1.t1_build audit  --replay-cache /tmp/t1_replays.pkl

# smoke runs: a model, 20 test turns; and two training steps on 8 items per split
uv run skillpng eval -c configs/t1.yaml --set model.model_id=/path/to/qwen3.5-9b \
  --set eval.limit=20 --set eval.condition=none
uv run skillpng train -c configs/t1.yaml --set model.model_id=/path/to/qwen3.5-9b \
  --set benchmark.limit=8 --set train.batch_size=4 --set train.epochs=1 \
  --set train.eval_every=1 --set train.eval_items=4 --set train.run_name=t1_smoke
python -m skillpng.benchmarks.t1.t1_report runs/t1/t1/eval/test-none.jsonl

# the baseline, then an image: same seed, same split
uv run skillpng eval -c configs/t1.yaml --set eval.condition=none
uv run skillpng eval -c configs/t1.yaml --set eval.condition=skillpng \
  --set eval.image_path=runs/t1/.../best.png

# optimize
uv run skillpng train -c configs/t1.yaml

# read the run
python -m skillpng.benchmarks.t1.t1_report runs/t1/<model>/<run>/eval/test-none.jsonl \
  --against runs/t1/<model>/<run>/eval/test-skillpng.jsonl
```

**The paper's decoding** is temperature 0.1, top-k 10 and 4,000 new tokens. It is not the
default; add it per command:

```bash
--set model.generate.do_sample=true --set model.generate.temperature=0.1 \
--set model.generate.top_k=10 --set model.max_new_tokens=4000
```

## 7. Verification

- **Oracle:** the gold answer, run through the whole pipeline on test (extraction, execution,
  scoring), reaches every T1 metric's maximum in every domain: tool and parameter
  P/R/F1/accuracy 1, cache EM 1, code success 1, and a headline of 1.0000.
- **Do nothing:** `<CODE>print("No planning needed")</CODE>` on test gives code success 0, tool
  and parameter F1 0, no calls on all 1,400 turns, and a headline of exactly the floor, 0.2479
  (0.2200 on val).
- **Aggregation parity:** hand-made per-turn records, written in T1's file format and run
  through T1's own aggregation scripts, agree with `t1_report` to within 1e-9 on every metric and
  domain.
- **End-to-end parity:** T1's evaluation and this adapter score the same generations turn by
  turn, on file 1 of every test domain for four synthetic predictors. Tool and parameter counts
  agree on every turn. The execution outcome agrees on every turn except leak-dependent ones,
  which the split excludes, and, for a predictor that changes one argument, one turn that reads a
  variable bound at an earlier turn (§3).

## 8. Quick reference

```
task              write the Python plan for one user turn of a travel dialogue; it is executed
corpus            T1 at revision 7a3e583: 9 domains, 13,500 dialogues, 61,150 user turns
item              one user turn, teacher-forced; id domain:hf_split:file:ID:turn
split             400 / 200 / 1,400 from T1 train / validation / test, one item per dialogue
eligible          has a gold plan, gold never raises, gold identical to T1's (no leaks)
prompt            T1's prompt, zero-shot, conventions stated, data/t1_prompt.txt (sha256 in the manifest)
target            <CODE>\n{gold plan stripped}\n</CODE>
answer            the last <CODE> block after the last </think>
execution         in a worker, on a copy of the gold state before the turn, 30 s timeout
headline          cache_em: cache summaries after the code == after gold
floor             0.2479 test, 0.2200 val for code that does nothing
report beside it  T1's per-domain metrics + macro avg, per-item code success, no-call share,
                  timeouts, gold_kind breakdown, paired bootstrap
budgets           max_target_tokens 512, max_sequence_tokens 16384, max_new_tokens 4000;
                  vLLM --max-model-len 20480
not scored        the wording of seek_information questions (no BLEU, no BERTScore)
not comparable    to the paper: subset, zero-shot, no leak-dependent turns
```
