# Write a skill for T1

You are writing a skill: a compact Markdown document of guidance for a language model. The skill is appended to the model's system prompt as its own `## Skill` section, and the model then answers every task of a benchmark under that combined system prompt. The model's weights are frozen and the skill never changes once written. The same skill is used unchanged with several different models, with and without a separate reasoning phase.

## The benchmark

Each task is one user turn of a multi-turn travel-planning conversation between a user and an assistant, about flights, hotels, restaurants and attractions. The model writes the Python plan for that turn, and the plan is executed. A plan can call tools that search a travel database, narrow, sort or locate earlier results and shift dates; ask the user for missing details with `seek_information`; and keep results for later turns with `save_to_cache`, reading them back with `get_results_from_cache`.

The model sees the conversation up to and including the user's last message, and the cache summary: a dict from each cache key to a summary of the query behind the saved result, usually with its number of matches. It never sees the results themselves. Both are always the correct ones, built by the correct plans of the earlier turns, never by the model's own earlier answers.

In the training split, about seven in ten turns call tools, about one in five only asks for missing details, and the rest either do both or only read the cache.

## How an answer is read and scored

- Everything up to the last `</think>` is dropped, and the last `<CODE>...</CODE>` block in the rest is executed. A response without a complete block counts as empty code, which changes nothing.
- The code runs where every tool is already defined, on the state the correct plans have built up to this turn: the cache holds exactly what the cache summary shows.
- The score is cache exact match: 1 when the cache summaries after the model's code equal those after the correct plan, compared as a collection of summary strings with the key names ignored, else 0. The metric is its mean over tasks.
- A summary spells out the query behind a result: the tool's parameters, the earlier result a filter was applied to, and usually the number of matches. So every saved result must come from the same tool, applied to the same earlier result, with the same parameter values. A missing or extra parameter, a different value, a result left unsaved, an extra saved result, or a save under a key the cache already holds, which replaces that entry, scores 0.
- Code that raises an error stops there, so whatever it would have saved afterwards is missing. Code that runs longer than 30 seconds scores 0.
- When the correct plan only asks for missing details, or needs nothing new, the turn scores 1 exactly when the code leaves the cache unchanged. The wording of a `seek_information` question is not scored.

## What a good skill for this benchmark covers

- Deciding what the user's last message calls for, read against the whole conversation and the cache summary: a new search, a filter or sort of a result already in the cache, a question about missing details, or nothing new.
- Knowing when a tool can be called: which of its parameters are mandatory, so that the model asks exactly when a mandatory value is missing, asks only for those, and searches as soon as all of them are known.
- Turning what the user said into parameter values: every stated preference and no unstated one, values kept as the user wrote them, dates the user only implies (such as a stay given in nights) worked out exactly, and ranges and lists in the shape the TOOL CONFIG documents.
- Building on earlier results: when to read a cached result back and narrow it instead of searching again, which key to read when several could fit, and saving every new result under a new key.
- Checking the code before answering: that it runs as written, and that it saves every result the turn calls for and nothing else.

The task prompt already states the output format and T1's planning rules, and the system prompt is a single sentence. The skill should add procedure for applying those rules, not repeat them.

## Requirements for the skill

- Write procedural, generalizable rules: how to read the task, how to decide, and how to check an answer before committing to it. Every rule must help on tasks you have not seen.
- Include no instance-specific content: no cities, dates, names, prices or other values, and no conversation wording from any particular task. The tool and parameter names in the TOOL CONFIG are the same for every task, and you may use them.
- Leave the answer format to the task prompt. Do not restate, rephrase, extend or override its OUTPUT FORMAT, and do not contradict any of its rules; the skill adds to the system prompt and the task prompt and replaces no part of either.
- Address the model directly, in plain Markdown: short paragraphs, bullet lists, and headings of level three (`###`) or lower, since the skill already sits under a level-two heading. No code blocks, no preamble, no closing remarks.
- Keep it compact: at most about 1,500 words. Shorter is better when nothing is lost.

## Output

Return the skill and nothing else, wrapped in <skill> and </skill>.
